# passthrough_seek：拖动后播一两秒就跳台 —— 根因与当前实现

> 本文是 `summary_20260905_SEEK_SOURCE_BUDGET_CN.md` 的续篇小结，只覆盖
> 2026-09-08 ~ 09-10 这一段：症状收敛、排错过程中走过的弯路、最终两个根因，
> 以及**当前的实现形态**（重点在第 4 节）。

---

## 1. 症状

源预算方案上真机后，容器、内容、音频、静态快照都已通过，只剩一个现象反复出现：

- 从头播放正常，已缓存位置点击也正常；
- **拖到尚未编码的位置，看到新画面一两秒，然后自动跳到下一个视频**；
- 另外：某个媒体根下的 8K 片子，播放器一律报"视频不支持"。

关键措辞是用户说的**"看到新画面"**——数据到了、解码成功了、画面画出来了，然后停了。
所以从一开始就不该往"画面/编码质量"方向找。

---

## 2. 踩过的坑（按时间顺序，都是错误方向）

### 2.1 把它当成画面问题，改坏了本来正常的东西

看到"跳转后先马赛克一下"就去动 encoder tier、`hvcC` 参数集、stsd。结果是
**原来正常的画面被改坏了**，而原始的跳台问题一点没解决。最后把这批改动整体
revert（`c472042`），画面立刻恢复正常。

> **教训：一次只追一个已确认的症状。**用户报的是"跳转失败"，"跳转后马赛克"是
> 次要现象，不该在主问题没解决前动它——尤其不该动会影响全局画质的编码参数。

### 2.2 用 `TestClient` 量 TTFB，量了个寂寞

`TestClient` 会把流式响应**整个缓冲完**才返回，所以量到的 11~13 秒其实是
"生成完整整 50MB 回复的时间"，不是首字节时间。真实 uvicorn 上同一路径是 0.2s。

> **教训：任何涉及 StreamingResponse 时序的测量，必须起真实 uvicorn，不能用 TestClient。**

### 2.3 "线程池被占满"假说

播放器同时开十几路连接，每个响应体最长会在 `wait_for_frame` 里阻塞 20 秒，
看起来很像 anyio 默认 40 个线程令牌被耗尽。写了探针实测：开 24 路"只收响应头、
不读体、也不关闭"的连接，`borrowed` 全程为 **0**——传输层背压会让 uvicorn 停止拉
生成器，阻塞中的体并不占令牌。假说否掉。

### 2.4 把 8K 当成"分辨率/规格"问题

其实和 8K 无关，和**盘**有关，见 3.1。日志特征具有很强的误导性：
`[WinError 1005] 此卷不包含可识别的文件系统`，栈顶在 `<frozen ntpath> realpath`，
看上去像磁盘坏了。

### 2.5 复现方式错了两次

- 第一次复现：三路并发、按内容速率限速消费 —— **复现不出来**，三路都正常应答。
- 第二次复现：顺序重开，但每路只读 4MiB 就丢弃 —— **也复现不出来**，TTFB 稳定 0.17s。
  因为起点始终落在已编码区间里。
- 第三次才对：**读完整段承诺的字节，再从末尾重开** —— 一次命中，
  第 6 次请求触发编码器重建，TTFB 3.39s。

> **教训：复现播放器行为时，"读多少就丢弃"这个参数决定了会不会踩到 bug。
> 必须让客户端走到承诺范围的末尾。**

### 2.6 有一个真修，但不是主因

`eb9d669`（响应体每吐一块就刷新 `last_hit_at`）确实修掉了一个真实缺陷：
一路正在被读的回复，因为没人更新"最近命中时间"，2 秒后会被判定为无人跟随而被抢走。
但它不是本次跳台的主因，单独上它并不能解决问题。保留。

## 3. 两个根因

### 3.1 挂载卷拒绝 `Path.resolve()`

某个媒体根是挂载卷，**`Path.resolve()` 在它上面直接抛 `OSError [WinError 1005]`**，
而 `os.stat` / `os.path.abspath` / `open()` 对同一路径全部正常。原因是 Windows 的
`resolve()` 会 `CreateFile` 去问 final path name，这个卷不实现该查询。

seek 路径上每个请求要调它三次（两次建缓存 key、一次进编码入口），所以该卷上的
**每一个**片子的 seek 请求都在进入任何业务逻辑之前 500 掉，播放器只能报"不支持"。

**修法**：媒体路径一律用 `os.path.abspath`（纯字符串，不碰文件系统）。在
`resolve()` 能成功的卷上两者返回值完全相同，已实测验证 —— 所以缓存 key 不变，
**已编码的帧缓存不会作废**。

统一走 `http_app/routes_media.py: _media_key_path()`，另加
`pipeline/pynv_stream.py: iter_pynv_passthrough_annexb_frames()` 的编码入口。

### 3.2 回复的末尾与编码前沿，用了两个不同的基准

这是跳台的真因。日志把它写死了：

```
01:20:10.424  请求 bytes=<offset>-
01:20:12.623  PyNv frame stream begin: start=1098.000   ← 编码器被整个拆掉重建
01:20:13.668  206                                        ← 3.2 秒后才回
```

编码器**从头到尾都在跑**（约 85fps，远超 30fps 输出所需），问题是它被反复拆掉重建，
而正在给播放器喂数据的那一路当场失去生产者。

两个基准不一致：

| | 用什么算 | 量级 |
|---|---|---|
| 一次回复的**长度** | 从**请求起点**算，最多 `MAX_SPAN_BYTES` | 48 MiB ≈ 450 帧 |
| 某位置**能不能被服务** | 从**编码前沿**算，`cursor + lead` | `lead` = 600 帧 ≈ 20 秒 |

回复的末尾就是播放器下一个请求的起点。于是每回合都把下一个起点往前推几百帧，
而编码器同期只推进几十帧。几轮之后播放器就问到了 `cursor + lead` 之外——
**那种请求不等待，它直接重定位编码器**：约 3 秒的管线重建，并且把所有还在从旧位置
流数据的响应体一起废掉。播放器看到画面停住，一两秒后跳台。

### 3.2b 顺带挖出的地雷：音频块偏移映射

`vmp4_frame_index_for_offset()` 对**落在交错音频块里的偏移返回 `None`**。三个调用方
都把 `None` 理解成"在第一帧之前"：seek 路径把它变成 `gop_index = 0`，于是
**片子中间几 MB 处的一次重开，把编码器打回 0:00**，那一次回复耗时 **347 秒**。

## 4. 当前实现（重点）

### 4.1 整体形态（未变的部分）

`/passthrough_seek` 的 `slot_frames` 后端提供一个**虚拟 MP4**：
`ftyp + moov + mdat`，单 moov，字节布局在任何编码发生之前就完全确定。

- 每个输出帧有**固定字节预算**，所以 `co64` / `stsz` / `stts` / `stss` / `stsc` 可以先写死；
- 预算的**总量**由实时路径同一条码率规则决定
  （`min(PASSTHROUGH_HEVC_BITRATE, 源码率×MULTIPLIER)`，再除以 headroom 覆盖 filler），
  并有「每像素每帧比特」下限兜住高帧率；
- 预算的**分布**默认是**平坦的**：每个 GOP 等额，GOP 内按 IDR 权重拆分。
  （见 7 节修法四：早期版本继承源 moov 的比特分布，那是错的——源的形状是离线 x265 的判断，
  我们的实时 NVENC 不认，低预算段直接饿死。`_BUDGET_FLATTEN=0` 可回到旧行为。）
- 编码出来不足预算的部分用 **HEVC filler NAL** 补齐；
- 虚拟文件总大小 = `源大小 × scale`（4K 约 2.06 倍、8K 到 3.0 上限），
  DIDL 声明的 `size` / `bitrate` 与 HTTP 层**逐字节一致**；
- 音频按 GOP 交错放置，直接透传源样本。

一个后台 filler 线程（`_vmp4_frames_filler_worker`）持有一个持久编码会话，
从某一帧开始**只向前**编码，把每帧写成 `frame_%06d.bin`。

### 4.2 一个请求是怎么被应答的

`_seek_vmp4_frames_response()`：

1. **结构性探测优先**。头部读、尾部探测（找不存在的尾 moov）直接从 layout 回答，
   有真实字节给真实字节，没有就给 filler。绝不为这类请求去等编码。
2. `vmp4_frame_index_for_offset()` 把起始字节映射到帧。落在交错音频块里时，
   **返回"第一个结束于该偏移之后的帧"**；`None` 现在只表示"确实在帧区域之外"。
3. `_vmp4_frames_wait_frame()` 等第一帧就绪（`RANGED_WAIT` 上限）。等不到但 filler
   在跑，**照样应答**——用 filler 填未编码部分，让播放器继续播，编码器在后面追。
4. 计算 `served_end`，这是本次修复的核心，顺序是：

   ```
   served_end = 已构建的连续前缀末尾
   if filler 在跑:        至少给到 start-1（不因未编码而缩短）
   MIN_SPAN:              至少 4 MiB
   if filler 在跑:        提升到 48 MiB（与已缓存地面同形状）
   MAX_SPAN:              封顶 48 MiB
   >>> _vmp4_frames_cap_to_reach(): 夹到「这次编码还够得着」的最后一帧 <<<
   ```

   `_vmp4_frames_cap_to_reach()` 取 `min(cursor + lead, frame_count-1)` 那一帧的末尾字节，
   把 `served_end` 夹在它以内。**这保证播放器的下一个请求永远落在窗口内**，
   于是那个请求是靠"等几毫秒"被应答的，而不是靠重启编码器。

   - **跳转本身完全不受影响**：那时 `cursor` 就在请求处，`lead`(600 帧) 比
     `MAX_SPAN`(≈450 帧) 还宽，夹不到，仍然给满 48 MiB。
   - 只有**已经跑到生产前面**的播放器会被拉回来，而且正好拉回到"等一下就有"的位置。
   - 如果起点本身已经超出可达范围，不夹（那时确实需要重定位），否则只会答 503。

5. 响应体 `iter_vmp4_frames_range()` 边发边等：遇到还没落盘的帧，用
   `_vmp4_frames_body_waiter()` 阻塞等待（上限 `BODY_FRAME_WAIT`），
   只有 filler 停了/失败了才返回 filler 字节。
6. 外层包一层 `_vmp4_frames_streaming()`：**每吐一块就刷新 `last_hit_at`**，
   保证正在被读的这一路不会被判定为无人跟随而被抢走。

### 4.3 filler 的调度规则

`_vmp4_frames_ensure_filler()`：

- `covered = start_frame <= need_frame <= cursor + lead` → 直接复用，刷新 `last_hit_at`；
- 未覆盖但**仍有人在跟随**（`last_hit_at` 在 `FOLLOW_WINDOW`=2s 内）且还在冷却期内 →
  保持不动，让它继续向前推进，请求那边等或 503 重试；
- 真正的 seek（没人跟随）→ 立即重定位：`stop_event` 停旧的，新线程等旧的
  `done_event` 交接（`HANDOVER_TIMEOUT`=20s）后再申请 Matter；
- 其他片子的 run 会被按"最久未读"退休，避免 Matter 池（`PT_MAX_CONCURRENT`）耗尽。

### 4.4 当前实测（复刻播放器模式：读完一段就在末尾重开）

| | 修复前 | 修复后 |
|---|---|---|
| 编码器重启次数 | 第 6 次请求触发，之后还有一次退回 0:00 | **整轮 1 次**（初始那次） |
| 跳转后各次 TTFB | 3.39s；退回 0:00 那次整段 347s | **0.17 ~ 0.20s** |
| 吞吐 | — | 约 3 倍实时，全程不断流 |

首次 seek 仍需约 1 秒起编码器（冷启动更久：解码器打开 + seek + TensorRT 预热），
这是 GPU 侧的下限。

### 4.5 相关开关（当前默认值）

| 名称 | 默认 | 作用 |
|---|---|---|
| `PT_PASSTHROUGH_SEEK_VMP4_FRAMES_SOURCE_BUDGET` | `True` | 启用逐帧预算计划 |
| `PT_PASSTHROUGH_SEEK_VMP4_FRAMES_BUDGET_FLATTEN` | `1.0` | 1 = 每 GOP 等额（默认）；0 = 继承源分布 |

| `PT_PASSTHROUGH_SEEK_VMP4_FRAMES_MAX_SPAN_BYTES` | 48 MiB | 一次回复最多给多少 |

`lead` 不是配置项，由 layout 推导：`max(gop*2, fps*20)` = 600 帧 ≈ 20 秒。

## 5. 排障方法论（本轮验证有效的）

1. **先看日志的"没发生什么"**，不是"发生了什么"。本轮的突破口是
   `retiring idle filler: idle=12.3s` 这一行——倒推出"某个请求进来后从没走到
   `ensure_filler`"，直接把嫌疑范围砍掉一半。
2. **卡住就 dump 全部线程栈**（`faulthandler.dump_traceback`）。一次 dump 就看清了
   是编码线程在跑、请求线程在等、还是响应体在发。
3. **复现必须复刻播放器的真实读取模式**，尤其是"读多少就丢弃"这个参数（见 2.5）。
4. **起真实 uvicorn，不要用 TestClient**（见 2.2）。
5. **假说要能被实测否掉**。线程池假说写了 20 行探针，5 分钟就否掉了（见 2.3）。

## 6. 后续可优化方向

- **首帧延迟**：冷启动约 1 秒（暖机）/ 更久（冷）。若要做到瞬时，只有预编码
  （`cache_file`）或 seek 落点先出低规格画面两条路。
- ~~**8K 首 GOP 预算贴地板**~~ —— 已做（地板随像素缩放，且预算已抹平）。
- **残余截断**：抹平后仍有约 3/1200 的帧冲破单帧 VBV 被截断。这是 NVENC 在硬帧上
  的率控失准，headroom 闭环只能压低平均而消不掉尾部。要根治得让超标帧不产生坏画面
  （重编码 / 更宽的 VBV / 更大的 slot），三条都有代价，需要先实测收益。
- **8K 顶到 `_BUDGET_MAX_SCALE`**：像素多且帧率高时，`_MIN_BITS_PER_PIXEL` 下限
  会被 3.0 倍上限截断。要么抬上限（文件更大、带宽更高），要么承认 8K 高帧率下画质有损。
- **`RANGED_WAIT` 已近乎无效路径**：filler 在跑时现在总能应答，该超时只在
  filler 尚未建立/已失败时生效，可以考虑简化。
- `_vmp4_frames_served_end()` 与 `_iter_vmp4_frames_ready_stream()` 里对
  `vmp4_frame_index_for_offset()` 返回 `None` 的处理仍按"init 区域"写，
  现在语义已收窄，可以再收一遍。

## 7. 追加一轮：8K 马赛克（2026-09-10 晚）

### 症状与提问

三段实测：两段 4K 画面正常，第三段 8K **马赛克严重**。用户问：“难道没有沿用 8K 视频本来的码率吗？”

### 答案：沿用了，但沿用码率 ≠ 沿用画质

源 28.39 Mbps，我们的预算 mean = 115 KiB/帧 × 30fps = 28.3 Mbps，逐 GOP 继承，一分不差。
损耗出在后面三层：

**1. 40% 的字节被当成 filler 扔掉了（最大一层）**

`RATE_HEADROOM = 0.6` 让编码器只编到预算的 60%，剩下用 filler NAL 补齐固定字节数。
实测每个档位都精确落在 0.6 倍：

| 预算 | NVENC 实际中位 | 比例 |
|---|---|---|
| 48 KiB | 30.6 KiB | 0.64 |
| 95 KiB | 62.6 KiB | 0.66 |
| 160 KiB | 99.6 KiB | 0.62 |
| 256 KiB | 151.8 KiB | 0.59 |

所以 8K 真正用于画面的只有 **17~19 Mbps**。

**2. 实时 NVENC ≠ 离线 x265**

源是离线多遍 x265；我们是 `preset=P1` + `ultra_low_latency` 实时单遍。同码率下差一档以上，8K 尤甚。

**3. 超预算的帧被截断 → 突发马赛克**

现场那一段 **281 帧被截断**（中位超 13%，最高 213%）。截断的 HEVC 帧是坏帧，一路花到下一个 IDR（≤60 帧 ≈ 2 秒）。
4K 段全程只有 1~2 帧被截断——这就是 4K 正常、8K 不正常的直接分界。

### 修法一：headroom 改成闭环

一个常数服务不了两种分辨率。实测（各自的真实预算）：

| | 4K | 8K |
|---|---|---|
| headroom 0.85 时超预算帧 | **0/60** | 7/40（18%） |

低到 8K 安全 → 4K 白白浪费；高到 4K 高效 → 8K 帧帧坏。所以改成按 GOP 判定的闭环：
给得快、收得慢，稳定在“超预算帧罕见”的位置。

两个被实测打回来的错误设计：

- **按帧反应**（单帧超标就 ×0.82）比固定常数**还差**：一次孤立超标把码率砍 18%，慢速上探再也追不回来（15.5 vs 17.1 Mbps）。改成按 GOP 窗口。
- **对编码器修不了的超标也回退**：某些帧已经顶到 QP 上限，是这段内容能达到的最小尺寸，降目标只会饿死本来守规矩的帧。实测这让 headroom 一路塌到 0.46 而超标照旧。
  现在用 `len(au) < 1.5 × target` 区分“可控超标”和“已饱和”，后者只保持不动。

### 修法二：预算量级不再继承源码率

先做了一版「8K 预算 ×1.5」（按输出像素分档），实机测下来**还是马赛克**，尤其是从头播放和每次切换之后。
量出来的数字说明了为什么：

| | 每像素比特（有效画面） |
|---|---|
| 4K（用户说正常） | **0.069** |
| 8K ×1.5 后 | **0.029** |

8K 每像素只有 4K 的 42%。而这不是「倍数不够」这么简单——**倍数本身就是猜的**。

真正的问题是用户点破的：**处理之后需要多少比特，由输出分辨率和内容决定，和源文件当初编成多少码率关系不大。**
两个 8K 源，一个 20 Mbps 一个 60 Mbps，经过同一个 NVENC 编到同样的 8192×4096，需要的比特是同一个量级。
继承源的**绝对量级**，等于让一个廉价编码的源把我们一起饿死。

值得继承的是源的**形状**（哪一段忙、哪一段静止），这部分保留。量级改用**实时路径自己的规则**：

```
目标画面码率 = min(PASSTHROUGH_HEVC_BITRATE, 源码率 × PASSTHROUGH_HEVC_SOURCE_MAX_MULTIPLIER)
字节预算带宽 = 目标画面码率 / RATE_HEADROOM      # 预算还要覆盖 filler
scale        = 字节预算带宽 / 源码率              # 上限 BUDGET_MAX_SCALE
```

于是输出带宽与源原本的码率脱钩：

| | 源码率 | scale | 输出带宽 |
|---|---|---|---|
| 4K | 32.4 Mbps | 2.056 | **66.7 Mbps** |
| 8K | 28.6 Mbps | 2.327 | **66.7 Mbps** |

**两个一致性坑：**

1. scale 现在**连续依赖 duration**，而 DIDL 从库索引取、HTTP 从 `probe_cached` 取。差一点点就会声明两个不同的字节数。
   → 两边都改成从同一个 `probe_cached` 取 size 和 duration，并把 scale 四舍五入到 3 位。
2. 第一版把 scale 加进了 `_seek_declared_total`——那是**三种后端共用**的路径（含把真实文件补齐到源大小的 cache 文件路径），
   12 个既有表征测试当场挂掉。frames 后端本来就用 `layout.total_size`，scale 只该出现在 layout 和 DIDL 两处。

端到端验证（DIDL 与 Content-Range 必须逐字节相等）：

```
4K  源 5,681,480,661   DIDL/HTTP 均 11,681,124,239  2.056x
8K  源 10,550,264,403  DIDL/HTTP 均 24,550,465,265  2.327x
```

### 修法一、二的效果（8K，180 帧真实内容，均在 30fps 下测得）

| | 有效画面码率 | 截断帧 |
|---|---|---|
| 继承源量级（115 KiB/帧，固定 0.6） | 16.0 Mbps | 18/180 |
| 平坦 ×1.5（172 KiB/帧，闭环） | 28.8 Mbps | 1/180 |
| **实时对齐（270 KiB/帧，闭环）** | **49.0 Mbps** | **0~1/180** |

完整实机跑：10 秒内 headroom 爬到上限 0.90 且**全程 `over=0`**，无一帧截断；seek 延迟不变，0.17~0.21s。

**注意 4K 也一起从 30 → 67 Mbps**（同一条规则、同一个目标）。画质会更好，带宽翻倍。

> **这些数字全部是 30fps 下测的，而服务端实际跑 40fps。** 上线后用户反馈「还是有显著马赛克」，
> 于是有了下面两轮——修法三找出帧率这个隐藏变量，修法四找出真因。

### 修法三：帧率不能再无声地决定画质

**用户问：“用户可能会设置为 60FPS，必须算好。”** 这一问揭出一个隐藏缺陷。

预算量级是「比特/秒」，与帧率无关；而每帧拿到多少 = 带宽 ÷ 帧率。于是提高输出帧率
= 同样的字节摊到更多帧上，**每帧画质按比例崩，而且没有任何提示**：

| | 30fps | 40fps | 60fps |
|---|---|---|---|
| 4K | 271K / 0.265 bpp | 203K / 0.199 | 136K / 0.133 |
| 8K | 269K / **0.066** | 202K / **0.049** | 135K / **0.033** |

> 参照：4K@40 = 0.199 bpp 用户反馈正常；8K@40 = 0.049 反馈马赛克。

而且我们踩了一个更基础的坑：**服务端实际跑 40fps，而此前所有实测都用了 scratchpad
里一份旧 env（30fps）**。“预算翻倍了为什么还马赛克”——多出来的字节进了多出来的帧。

修法：给「每像素每帧比特」加下限，让帧率去花带宽而不是花画质
（`_MIN_BITS_PER_PIXEL`，默认 0.066 = 8K@30fps 的水平）。它只在像素多且帧率高时生效，
4K 在任何档位都远在其上，完全不受影响。

**注意 8K 每一档都顶到 `_BUDGET_MAX_SCALE=3.0` 的天花板**，所以下限在 8K 上没能完全生效：
守住 0.066 bpp 在 40fps 要 4.1 倍源大小、60fps 要 6.2 倍。

### 修法四：不再继承源的比特分布（真因）

**用户问：“我们原来 live 模式完全没问题，当时不是同样传输的吗？”** 这一问直接问到根子上，
并且推翻了整个「源预算」方案的**核心前提**。

先看实际落盘的字节（不是预算）：

| | 每帧预算 | **实际写出** | 有效画面码率 |
|---|---|---|---|
| seek 8K | 190 KiB | **125 KiB** | **40 Mbps** |
| live 8K | 无单帧上限 | — | **50 Mbps** |

**虚拟文件声明大了 3 倍，真正上画面的比特却比 live 还少 20%**，而且 live 一帧都不截断。

#### 证据链

| 观察 | 数字 |
|---|---|
| 截断帧全是 P 帧 | 418/418，IDR **0** 帧（随机应为 1.7%） |
| 截断集中在低预算段 | 89% 的截断帧预算 ≤160 KiB，而全片只有 25.8% 的帧在此区间 |
| 这些帧想要多少 | 中位 **123 KiB**，而它们的预算中位只有 **113 KiB** |
| 我们编码器的胃口 | P 帧全片中位 **113 KiB**、均值 120 KiB（24557 帧实测） |
| 源的预算摆幅 | 88 KiB … 711 KiB |
| IDR 权重是否冤枉 | 不冤：实际 3.55× vs 预算 3.8×，**校准是准的** |

**结论：源的形状记录的是「离线多遍 x265 觉得哪里便宜」，我们的实时单遍 NVENC 不认。**
它在哪儿都要差不多的字节。于是继承来的分布，其低端直接低于我们任何一帧的成本，
落在那里的帧全被截断——而截断的 HEVC 帧是坏帧，一路花到下一个 IDR。

**live 从不看源花了多少，每一秒都给同样的码率。这就是两者的全部差别。**

#### 对照实验（同一总字节，只改形状）

| 起点 | 源分布 | 平坦 |
|---|---|---|
| 0s | 15/300 截断，24.7 Mbps | **1/300，52.8 Mbps** |
| 165s | 4/300，33.8 | **0/300，67.5** |
| 600s | 0/300，75.4 | 1/300，63.8 |
| 1200s | 2/300，55.9 | **1/300，66.1** |
| **合计** | **21 帧，均值 47.5 Mbps** | **3 帧，均值 62.6 Mbps** |

坏帧少 7 倍，上画面的比特多 32%，**总字节一分未变**。片头那段——正是用户报告最差的地方——
源的形状只给 24.7 Mbps，而 live 在同一段给 50。

顺带：每帧地板也改成随像素缩放。一个 48 KiB 的常数对 8K 只有 0.011 bpp，
而那里一个 P 帧要 123 KiB；4K 及以下仍用该常数，只有被饿死的分辨率会变。

#### 效果

全片预算 p1 到 p90 全部为 249 KiB，`<=160 KiB 的帧 0.0%`（原 25.8%），不再有饿死的段。

### 这一轮又踩的坑

**a. 建议用户迁就实现。** 我先后提出降帧率、降分辨率、加带宽三条，被用户否掉：
*“用户自己显卡千差万别，不可能限制 FPS。降低 4K 也不可能强制，一些头显支持 8K。”*
这是对的——最终方案没有动任何用户可见设置，只是把同样的字节分配对。

**b. 拿旧配置做测量。** scratchpad 里那份 env 是 30fps，服务端是 40fps，
一整轮结论都建立在错误前提上。**测量前先从 `Settings().server_env()` 导出真实配置。**

**c. 用错的样本证伪。** 第一次测「平坦 vs 源分布」选在 600s，那段预算本来就高（252K–1243K），
两种方案都不截断，于是得出「形状无关」的错误结论。
**要证伪一个假设，必须选它会失效的样本**——低预算段。

### 相关开关

| 名称 | 默认 | 作用 |
|---|---|---|
| `PT_..._RATE_ADAPT` | `1` | 0 = 固定 headroom（旧行为） |
| `PT_..._RATE_HEADROOM` | 0.75 | 闭环起始值；也是预算换算用的标称值 |
| `PT_..._RATE_HEADROOM_MAX` / `_MIN` | 0.90 / 0.45 | 闭环上下界 |
| `PT_..._BUDGET_MATCH_LIVE` | `1` | 0 = 回到继承源量级（虚拟大小 = 源大小） |
| `PT_..._BUDGET_FLATTEN` | **`1.0`** | **0 = 继承源分布（旧行为），1 = 每个 GOP 等额** |
| `PT_..._BUDGET_MAX_SCALE` | 3.0 | 虚拟文件相对源大小的上限倍数 |
| `PT_..._MIN_BITS_PER_PIXEL` | 0.066 | 每像素每帧比特下限，帧率去花带宽而非画质 |
| `PT_..._FLOOR_BITS_PER_PIXEL` | 0.03 | 每帧地板随像素缩放（8K→123 KiB，4K 不变） |
| `PT_..._FLOOR_BYTES` | 48 KiB | 每帧地板的绝对下限 |
| `PASSTHROUGH_HEVC_BITRATE` | 50M | 目标画面码率上限（**seek 和 live 共用**） |

### DLNA 呈现（同一轮）

- seek 条目改名为 `[模式]原显示名`：`[GREEN]movie_LR_180_SBS` / `[ALPHA]movie_LR_180_FISHEYE_F180_alpha`。
  **alpha 必须保留自己的 `_FISHEYE_F180_alpha` 投影标记**——它描述的是输出而不是源，
  用源的 `_SBS` 命名会让播放器把鱼眼内容按等距投影，画面会错。
- **live / seek 二选一**：一个模式只列其中一个（`PT_PASSTHROUGH_SEEK_DLNA`）。
  没有 seek 形态的模式（two_dvr / superres / rm / face_beauty）保留 live 条目。
  顺带堵掉了 superres 那个「列出来但点了 409」的死项——浏览条件原本是 `mode != "two_dvr"`，
  而后端白名单是 `{green, alpha}`，两处不同源。
- **UI 开关**：Alpha 卡片新增齿轮，绿幕对话框同段加入「虚拟文件 / 直播流」单选 +
  说明文字 + 「有问题可以试直播流」提示，默认虚拟文件。中英日三语。
  一个键 `passthrough_playback_mode` 推导出 `SEEK_ENABLED` 与 `SEEK_DLNA`（路由和广告必须一致）。

### 尚未定论

播放器开头提示“视频编码过大是否继续”：DIDL 声明的是 `size×8/duration`，
和同一文件的普通 `/media` 条目用的是同一个公式，所以不是 seek 项特有的异常。
没有确凿证据前不动它。注意虚拟文件现在声明 2~3 倍于源的大小，这个提示可能更容易出现。
