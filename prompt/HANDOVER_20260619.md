## Passthrough Seek Revival Research

- User wants to revisit the previously abandoned `/passthrough_seek` route after
  the SI progressive virtual MP4 route proved draggable on Quest3 VR players.
- Current state:
  - `/passthrough_seek/{name}` still exists but remains default-off via
    `PT_PASSTHROUGH_SEEK_ENABLED=0` and `PT_PASSTHROUGH_SEEK_DLNA=0`.
  - It currently declares a virtual estimated size as
    `PT_PASSTHROUGH_SEEK_HEADER_BYTES + estimate_for_media(...)`, maps
    byte ranges to time with `utils.byte_seek_map.map_byte_start_to_time()`,
    then starts a fresh realtime PyNv/FFmpeg producer from that time.
  - It is still not a byte-stable MP4 file. Prefix cache only stabilizes the
    first reserved bytes.
- Key comparison with SI progressive MP4:
  - SI succeeds because video samples are copied from the source MP4 unchanged;
    only the mixed AAC sidecar is generated. `pipeline/si_virtual_mp4.py`
    rewrites `moov` sample tables and serves a real virtual byte layout via
    `iter_virtual_range()`.
  - Passthrough green/alpha/2DVR re-encodes video. Sample sizes, offsets,
    codec config, keyframes, and sometimes resolution/FPS are not known until
    the output is encoded. A static MP4 `moov` cannot be made truthful from the
    original MP4's sample table.
- User-specified constraints:
  - declared file size should match the original source video;
  - declared duration should match the original source video.
- Feasibility notes:
  - Duration is easy at metadata/header level, but the track sample timing must
    still match the actual output FPS and audio timeline.
  - Source-size declaration is only safe if the generated output can be kept
    at or below the source byte budget and padded to exactly the source size.
    Current PyNv HEVC default is `50M`, capped by `source_bps * 2.0`; that is
    not equivalent to "same size as source".
  - If the actual output exceeds the source size, truncating to source size will
    corrupt the file/stream. A true MP4 path needs conservative per-source
    target bitrate or a retry pass, then valid padding/free space.
- Main blocker:
  - Reviving `/passthrough_seek` by only changing `Content-Length`, DIDL size,
    and duration will recreate the old fMP4/TS problem: strict players seek by
    container index and expect every Range response to be the same selected
    representation.
  - A real reuse of the SI method for passthrough means pre-encoding/nearline
    caching the transformed media, building truthful sample tables, and serving
    it as a byte-stable virtual MP4. That is closer to offline/nearline output
    than realtime passthrough.
- Suggested next experiment tiers:
  1. Metadata-only hidden experiment: add a guarded source-size mode for
     `/passthrough_seek`, keep DLNA hidden, set HTTP/DIDL size to source size
     and duration to source duration, then test the five VR players. Expected
     value is diagnostic; success is not guaranteed because bytes remain
     non-stable.
  2. True virtual MP4 prototype: encode the passthrough output into a cache or
     segment store first, build `ftyp+moov+mdat` using the SI virtual layout
     pattern, pad to source size when actual output is smaller, and serve with
     `iter_virtual_range()`.
  3. Production path: only expose the seek MP4 item after the byte-stable
     virtual/cache layout is ready; keep `/passthrough_live` visible as the
     fallback.
- Wrote the concrete Chinese plan summary:
  `summary/summary_20260619_PASSTHROUGH_SEEK_REWORK_PLAN_CN.md`.
- User clarified the execution preference: do not add a separate prototype URL;
  wire the VMP4 experiment directly into existing `/passthrough_seek` behind a
  new hard switch so VR devices can test the real entrypoint immediately.
  Updated the plan summary accordingly.

## Passthrough Seek VMP4 Oversize Cache Rebuild

- User clicked `72463_3840p` after the first cache build completed and got
  `409`.
- The build log in `debug_output/vmp4_cache_build` showed the cache build
  itself succeeded:
  - input/source declared size: `492,192,352` bytes
  - generated alpha cache size: `582,240,696` bytes
  - generated cache duration: about `214.997s`
- Root cause: VMP4 requires the served layout size to equal the source size,
  and the generated alpha MP4 exceeded that byte budget. The route correctly
  rejected it as `cache-oversize`, but leaving that as a permanent `409` blocks
  GUI/VR retest.
- Changed default VMP4 cache build bitrate from `source` to `budget`:
  - budget is computed from `source_size * 8 / source_duration` with safety
    margin.
  - alpha uses a stricter margin than green because alpha-packed output is
    larger than the source layout.
  - when an oversize cache is observed, the rebuild bitrate is further reduced
    by the observed `source_size / cache_size` ratio.
- Changed `cache-oversize` handling:
  - If missing-cache build is enabled, the route now queues a forced rebuild of
    that cache using the budget bitrate and returns `503 VMP4 cache rebuilding`
    with `X-Passthrough-VMP4-Phase: cache-oversize` plus build headers.
  - If build is disabled, it still returns the old explicit `409`.
  - The old oversized cache remains in place until the new temp build finishes
    and atomically replaces it.

## Passthrough Seek VMP4 Slot Annex-B Payload Writer

- Continued the slot backend toward real GPU GOP payloads.
- Reason:
  - PyNv realtime encoder returns raw HEVC Annex-B bitstream with start codes;
  - MP4 `mdat` samples referenced by `stsz/co64` must use length-prefixed NAL
    units;
  - writing raw start-code HEVC directly to `slot_XXXXXX.bin` would make the
    virtual MP4 inconsistent.
- Added helpers in `pipeline/passthrough_vmp4_slot.py`:
  - `iter_annexb_nal_units(...)`;
  - `hevc_annexb_to_length_prefixed_sample(...)`;
  - `write_vmp4_slot_hevc_annexb_payload(...)`.
- Behavior:
  - accepts both 3-byte and 4-byte Annex-B start codes;
  - strips trailing zero bytes from each NAL;
  - uses the layout's `nal_length_size` for MP4 sample prefixes;
  - raises `annexb-nal-missing` for empty/invalid raw streams;
  - raises `slot-payload-oversize` if the converted payload exceeds the slot
    sample budget.
- This gives the next real worker a stable write path:
  PyNv `Encode(...)` raw bytes -> length-prefixed MP4 sample -> atomic
  `slot_XXXXXX.bin` -> manifest `ready`.
