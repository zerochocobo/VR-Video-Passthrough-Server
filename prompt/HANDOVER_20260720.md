## RTX Video HDR research

- NVIDIA's comparison combines two independent NGX features: Video Super Resolution (VSR) and TrueHDR/RTX Video HDR. HDR is not another VSR quality level.
- Current project initializes the CUDA SDK with `THDREnable=0, VSREnable=1`; therefore no HDR option is active or exposed in UI.
- The SDK/native source contains TrueHDR controls (contrast, saturation, middle gray, max luminance), but the current Python path passes an empty THDR struct to a VSR-only feature.
- TrueHDR output is packed 10-bit ABGR10. Current realtime/offline pipelines are RGBA8 -> NV12/8-bit HEVC with BT.709 metadata and explicitly reject 10-bit input, so exposing a checkbox without a P010/Main10/HDR10 conversion and metadata path would produce invalid colors rather than real HDR.
- Recommended scope is offline TrueHDR first, with capability preflight, ABGR10 conversion, P010 HEVC Main10 encoding, BT.2020/PQ metadata, and HDR-source rejection/bypass; realtime DLNA HDR should follow only after player/TV compatibility testing.

- In this adaptive target, project-recognized 2:1 SBS VR sources output 8192x4096, while non-VR/2D sources automatically use 3840x2160. Offline filenames therefore use `_8K` for SBS VR and `_4K` for 2D.
- The previous 4K selector is now labelled `4K (3840x2160)`. A 2:1 VR source processed under that target retains its 4096x2048 player-friendly shape.
- Realtime and offline now split 2:1 VR frames before NGX evaluation for both target tiers. A 4K VR frame is evaluated as two 2048x2048 eyes; an 8K VR frame is evaluated as two 4096x4096 eyes. ## 8K VR RTX VSR 60 FPS performance investigation

- Investigated the reported offline 4096x2048 -> 8192x4096 SBS VR conversion at source 59.939 FPS, NGX `quality=4` (Ultra), NVENC `preset=p1`, and `hdr_look=natural`. The long run sustains about 24 FPS and finishes at 22.85 FPS including final audio mux.
- Hardware is NVIDIA GeForce RTX 5060 Ti 16 GB, driver 581.57, 180 W limit. During a 5-second reproduction, steady GPU telemetry showed SM 95-97%, memory controller about 48%, NVENC 24-44%, and NVDEC near idle. The reproduced rate was 21.9-23.3 FPS, final 22.99 FPS.
- This establishes a compute/NGX bottleneck, not a decoder, mux, disk, or NVENC bottleneck. Output throughput is about 0.77 billion pixels/s; 8192x4096 at 60 FPS needs about 2.01 billion pixels/s, or roughly 2.6x current throughput.
- `P1` is only the NVENC preset. It is already the fastest encoder choice and does not change NGX VSR inference quality/speed. A short Ultra/Natural/P7 test fell to 10.99 FPS, so P7 must not be used for this target.
- Controlled short tests: Ultra(4)/HDR off/P1 = 21.39 FPS; Medium(2)/Natural/P1 = 43.40 FPS; Ultra(4)/Natural/P7 = 10.99 FPS. HDR-look is not the dominant cost. Even Medium did not reach 60 FPS in the current pipeline/hardware.
- The split-eye path performs two serial NGX evaluations per output frame, one 2048x2048 -> 4096x4096 evaluation for each eye. `RtxVsrBridge.process_cupy_rgba()` synchronizes before and after every evaluation, and the native device-pointer bridge uses synchronous `cuMemcpy2D` into and out of CUDA arrays. This prevents useful cross-eye/frame overlap and adds copies, but the GPU saturation indicates removing Python/CUDA overhead alone is unlikely to produce the required 2.6x gain at Ultra.
- There is avoidable memory traffic before NGX: NV12 is converted to a full 4096x2048 RGB buffer, then four CuPy slice assignments form left/right RGBA inputs. A fused NV12-to-split-eye-RGBA CUDA kernel can remove the intermediate RGB buffer and slice kernels. Stage timing should be added before judging its actual gain.
- Recommended implementation order: (1) add CUDA-event stage telemetry for decode wait, NV12 conversion/split, left NGX, right NGX, HDR, NV12 pack, NVENC, and mux; (2) fuse NV12 conversion plus eye split; (3) remove only demonstrably redundant synchronizations and use CUDA events for producer/consumer ordering; (4) investigate a native persistent CUDA-array interface so per-evaluation deviceptr<->array copies are avoided; (5) only then evaluate multi-stream/multi-instance eye concurrency, subject to NGX feature thread-safety and VRAM limits.
- Product expectation: 60 FPS at 8K SBS + Ultra on this RTX 5060 Ti should not be promised. Practical modes are Ultra at about 23-24 FPS, Medium around the mid-40s before further optimization, or a larger/faster GPU. A user-facing `60 FPS priority` mode would need an explicit quality tradeoff and likely adaptive quality; NVENC P1 alone cannot supply it.
- No production source code was changed during this investigation. Temporary benchmark outputs were written under `runtime_cache/tmp` for measurement.

### Whole-frame versus split-eye 8K benchmark

- Ran a process-local benchmark that bypassed split-eye detection without changing production source. All other parameters matched the reported case: `test_4k.mp4`, 4096x2048 -> 8192x4096, 300 frames / 5 seconds, NGX Ultra (`quality=4`), NVENC P1, CQ 19, and natural HDR-look.
- Whole-frame single NGX evaluation (`split_eyes=off`) succeeded and produced a verified HEVC 8192x4096 yuv420p file with 300 frames and 5.0058-second duration.
- Whole-frame progress was 20.14 FPS at 101 frames and 21.20 FPS at 213 frames; final measured processing rate was **21.01 FPS**.
- The equivalent 5-second split-eye benchmark measured 21.93 FPS at 110 frames, 23.33 FPS at 234 frames, and **22.99 FPS** final. The user's full-minute split-eye run also sustained about 24 FPS and finished at 22.85 FPS.
- Therefore whole-frame evaluation is about **8.6% slower** than the matched split-eye run (`21.01 / 22.99 - 1`). It does not improve performance and moves farther away from 60 FPS.
- Whole-frame GPU telemetry remained compute-bound at mostly 96-98% SM, about 47-50% memory-controller use, and roughly 23-35% NVENC use. The single larger NGX call does not recover enough launch/synchronization overhead to offset its less favorable processing shape.
- Benchmark artifact: `runtime_cache/tmp/rtx_vsr_bench_whole_8k_q4_natural_p1.mp4`.

### Split-eye pipeline optimization research and implementation

- Added opt-in offline stage telemetry controlled by `PT_RTX_VSR_STAGE_TIMING=1`. It reports CPU averages for decode wait, input synchronization, left/right NGX calls, output synchronization, NVENC and mux, plus CUDA-event averages for NV12 conversion, eye preparation, left/right VSR, HDR-look and RGBA-to-NV12. Default processing does not enable the event instrumentation.
- Baseline telemetry confirmed the dominant cost is the two NGX calls. Representative averages were left VSR 21.5 ms, right VSR 21.7 ms, NV12-to-RGB 0.15 ms, eye split/RGBA preparation 0.53 ms, HDR-look 0.77 ms and RGBA-to-NV12 0.73 ms. Decode, NVENC and mux are minor.
- Replaced the full-frame NV12-to-RGB allocation plus four CuPy eye-slice assignments with one fused `nv12_to_split_rgba` CUDA kernel. The split path now writes left and right contiguous RGBA inputs directly and no longer allocates the intermediate 4096x2048 RGB buffer.
- Compared the fused result with the pre-change split-eye result over 300 encoded 8K frames. FFmpeg SSIM was exactly `Y/U/V/All = 1.000000`, confirming identical decoded output and correct eye ordering. The measured throughput improvement is small and within run-to-run variance: roughly 0-1%, consistent with the removed stage being below 1 ms/frame.
- Tested skipping the bridge post-evaluation stream synchronization and tested submitting NV12 to NVENC without the final explicit stream synchronization. Results were 22.09 FPS and 22.04 FPS respectively versus about 23 FPS normally; neither optimization helped. Both experimental switches were removed, leaving the established synchronization behavior intact. The initial device synchronization is required because PyNv ThreadedDecoder uses an internal NVDEC stream that is not exposed to CuPy.
- Added opt-in native bridge telemetry controlled by `PT_RTX_VSR_NATIVE_TIMING=1`, rebuilt `pt_rtx_vsr_bridge.dll`, and measured input device-to-array copy, NGX evaluation, and output array-to-device copy separately. Timing mode adds synchronization boundaries only when enabled.
- At 600 eye evaluations, native averages per eye were: input copy 0.146 ms, NGX evaluation 18.516 ms, output copy 0.444 ms, total 19.106 ms. The CUDA arrays were already persistent across frames; eliminating both linear-memory/array copies would save only about 1.18 ms per full SBS frame, theoretically around 2-3% or less than 1 FPS. A complex direct texture/surface interface is not justified for the current target.
- SDK headers explicitly state NGX methods are not thread safe. The bridge also currently exposes one global feature instance. With observed SM utilization 96-98% and board power near the RTX 5060 Ti 180 W limit, two feature instances/streams would contend for an already saturated GPU and carry crash/thread-safety risk. No dual-instance production prototype was introduced.
- Final 10-second fused-path run processed 599 frames. Stable progress reached 22.88 FPS; final rate including completion/audio mux was 22.25 FPS. This remains consistent with the original roughly 23-24 FPS ceiling.
- Validation: RTX VSR focused suite `11 passed`; project suite `505 passed, 2 skipped, 61 subtests passed`, with four unrelated existing failures (missing Japanese translation keys and request-history output permission errors). A repository-wide unscoped pytest also incorrectly collects third-party tests under `reference/` and caches under `runtime_cache/`.
