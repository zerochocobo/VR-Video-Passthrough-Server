# Work Handover (2026-08-01)

## Request

After swapping in the mid=96 v0.2 restorer, starting the DLNA server stalled for
a long time in the "RM TensorRT startup warmup" phase (measured 412s), with no
real ETA/countdown, and it tripped a 300s startup timeout. First-pass fixes
treated it as a one-time first-build; the user then pushed back: if a user runs
offline first instead of realtime, the same thing happens the other way -- the
tool must not depend on operator ordering. That reframed it into finding the real
root cause.

## Root Cause

The ORT-TensorRT engine-cache filename embeds a hash. With no
`trt_max_workspace_size` set, ORT-TRT sizes the build workspace from the VRAM
free at build time, and that size is part of the hash. The realtime path builds
the RM engine *after* the RVM GPU warmup has grabbed VRAM; the offline/CLI path
builds it on a clean GPU. Different free VRAM -> different workspace -> different
hash, so whichever environment ran second did not hit the other's cached engine
and rebuilt it (a multi-minute stall).

This is systemic, not RM-specific: DA3's `runtime_cache/da3_trt/base/` had already
accumulated four different-hash engines from repeated rebuilds -- the same bug,
long unnoticed.

(An earlier hypothesis -- that a stale mid=64 engine was being mistaken for the
new one -- was real but secondary; even with a matching model the hash still
drifted by environment.)

## Done

### Root fix -- pin the TRT workspace (commits 721c105, cff30e3)

- New `config.ONNX_TRT_MAX_WORKSPACE_BYTES` (env `PT_ONNX_TRT_MAX_WORKSPACE_BYTES`,
  default 4 GiB): the single knob.
- Every production ORT-TRT session sets `trt_max_workspace_size` from it:
  `pipeline/demosaic.py`, `offline/da3_depth.py`, `pipeline/matting.py` (the
  dynamic-TRT fallback; the main RVM path already uses a static prebuilt engine),
  and `offline/nvds_stabilizer.py`.
- The hash is now independent of runtime VRAM, so every model produces/hits one
  engine regardless of which environment builds it first. No operator ordering.
  Swapping any model in future rebuilds exactly once.
- Build workspace is transient (freed after the build), so it does not compete
  with 8K decode/encode at runtime.

### Supporting startup fixes (commit 025eebd)

- `rm_trt_cached()` also requires each engine to be newer than its ONNX (mtime).
  A model swapped in after its engine reads as not-cached, so startup shows the
  "building" phase with a build-sized ETA instead of a 30s "warming" one. (This
  guards the "model newer than engine" case; the workspace pin above is what
  fixes the "engine present but hash mismatched" case.)
- `STARTUP_GPU_WARMUP_TIMEOUT` and the UI status poller `max_duration_sec`
  300 -> 900, so a legitimate first build is not cut off. Cached warmup is ~8s,
  so this ceiling is never approached normally.
- RM warmup build ETA 180 -> 420s to match the deep model.

## Verification

- demosaic: cleared the cache, built with no GPU warmup (hash 2425, 470s), then
  ran WITH the GPU warmup first -- it **hit 2425 in 7.9s** instead of building a
  different hash. Both environments converge on one engine.
- DA3 base (394 MB ViT): builds/loads cleanly under the 4 GiB cap in **10.3s, no
  OOM**. TRT does not fail on a small workspace; it just picks a tactic that fits.
- Cached RM warmup measured at ~8s.
- All four modules compile and their provider builders include the workspace key.

## Follow-up

- DA3 `large` (1.35 GB) was not force-rebuilt here (costly). Same ViT
  architecture as base, so 4 GiB should build it too (TRT falls back rather than
  failing); worth a spot check next time it's exercised, and
  `PT_ONNX_TRT_MAX_WORKSPACE_BYTES` can be raised if ever needed.
- Changing the workspace value rebuilds every engine once (workspace is in the
  hash), so pick a value and leave it.
- This change rebuilds DA3/matting/NVDS engines once each on first use after the
  update (same one-time cost demosaic already paid), then they are stable.

## Correction (2026-08-02): the workspace pin does NOT unify engines

Follow-up testing disproved the "one shared engine" claim above. md5 confirmed
the realtime-built and offline-built restorer engines have genuinely different
content (different build tactic), and realtime still rebuilds rather than hitting
the offline engine. So the ORT-TRT cache hash depends on the real GPU/VRAM state
at build time, not the configured workspace value (otherwise the same config
would hit). The earlier "hit 2425 in 7.9s" was a coincidence -- both runs
happened to have similar free VRAM.

Actual behaviour: offline and realtime each build their own engine (~50 MB each),
and each is stable on repeat starts (realtime re-start measured ~10s,
user-confirmed). The two are not shared; that is acceptable and not a per-start
rebuild. The 4 GiB workspace cap stays as a sane build ceiling but is not what
stabilises anything. Genuinely unifying them would need prebuilt/static engines
(EPContext, like matting's static_trt) -- not done. The timeout/mtime fixes in
025eebd remain valid.

- The restoration models are clean: **GFPGAN 1.2/1.3/1.4 and RestoreFormer++ are

## Done -- offline face beautification

New: `offline/face_beauty_engine.py` (inference core), `offline/face_beauty.py`
(CLI), `ui/pages/face_beauty_page.py`, `ui/widgets/face_beauty_trt_dialog.py`,
`ui/widgets/face_beauty_tuning_dialog.py`, `models/FaceBeauty/` (readme only;
`*.onnx` is gitignored). Wired through `tools_page` / `main_window` /
`process_helpers` / `offline_process` / `main.py` (frozen `face_beauty`
subcommand) / `icons.py` / three translation files.

Pipeline per face: YuNet detect -> 2DFAN4 68-point landmarks -> 5-point affine
warp to the ffhq_512 template -> GFPGAN/RestoreFormer++ -> BiSeNet-gated skin /
eye / teeth / lip retouch -> box+region mask -> paste back. Frame geometry is
untouched, so SBS/VR sources keep their layout and filename markers.

### GFPGAN must not run in fp16 (the important finding)

A TensorRT fp16 engine for GFPGAN **does not fail -- it silently returns a
darkened, washed-out face** (measured mean 83 / std 16 vs CUDA's 180 / 43 on the
same crop). Found only by eyeballing output frames. TRT fp32 is correct but
measured *slower* than CUDA (31 ms vs 25 ms) for a multi-minute build, so the
enhancer is pinned to the CUDA EP via `onnx_providers(..., use_tensorrt=False)`
and is excluded from `trt_cache_keys()` / `build_trt()`. Detector, landmarker and
parser use TRT fp16 and match CUDA output.

### Performance

Per-frame cost was dominated by CPU post-processing, not inference:
full-resolution `bilateralFilter` alone was 150 ms and five separate LAB
round-trips another 70 ms. Fixes: bilateral at half resolution with a fixed
kernel, and one shared LAB round-trip accumulating all tonal passes in place on
the channels they touch (`apply_lab_adjustments`). 299 ms -> 136 ms per frame;
720x1280 single-face video went 2.6 fps (CUDA) -> **5.6 fps**. Clean TRT build of
the three engines is ~92 s.

### Presets

FaceFusion ships no presets (its `.ini` is empty). Community guides converge on
blend 80-90 natural / 100 max, mask blur 0.3, detector score 0.5, so those seed
four presets in `face_beauty_engine.PRESETS`: `restore` / `natural` / `standard`
/ `strong`. The CLI layers `--beauty-preset` under individual flags (all tunables
default to `None` = inherit). `--preset` stays the NVENC preset, matching the
other offline tools.

`min_face_px` was replaced by `min_face_mode` (auto / loose / strict) resolved
per frame as a share of frame height -- an absolute pixel count means different
things at 720p and 8K VR.

### UI

Each tab (single + batch) carries `beauty settings` (preset dropdown + fine-tune
button + effect summary) and a `TensorRT` row (configure button + cache status),
both directly under the path row and kept in lockstep across tabs by
`_refresh_settings_rows`. All twenty-odd knobs live in the tuning dialog, grouped
beauty / quality / detection. Options persist under `face_beauty_options`.

## Also fixed (pre-existing failures)

- `tests/test_demosaic_chunk_model.py` still asserted the v0.1 restorer; commit
  ab7b34a moved to v0.2. Test updated, code unchanged.
- ja_JP was missing 14 keys (`modeldl.*`, `twodvr.*`) and failed the i18n parity
  test. Translated and reordered to the zh_CN grouping. **All three translation
  files are now at 521 keys and the suite is fully green (528 passed).**

## Follow-up / next

- Only validated on 720x1280 single-face footage. The real target is 8K VR, where
  faces are small and the equirect projection stretches them; `min_face_mode` and
  detector size will need recalibration against real VR material.
- **Next task: rebuild the offline flow as a GPU-resident pipeline and judge

# Work Handover (2026-08-01, part 3)

## Request

Commit the face-beauty work, then study the RM (mosaic) pipeline -- which shares
one path between realtime and offline and, for VR, detects the region, converts
to a flat view, processes, and converts back -- and rebuild the offline face
pipeline as a GPU-resident one, finally judging whether realtime is reachable.
After the realtime verdict below, the user scoped this to **offline GPU only**.

## Realtime verdict: not reachable with this model set

Per-model inference measured in isolation (one session alive at a time):
detector 9.0 ms, landmarker 5.4 ms, parser 42.3 ms, GFPGAN 55.4 ms. The standard
preset is therefore **112 ms/face of pure inference -- 8.9 fps** with zero pixel
work, zero IO and one face, against a 33 ms budget at 30 fps. GPU-ising removes
pixel movement; it cannot touch that 112 ms.

The only realtime-shaped option is a keyframe scheme (restore every Nth frame,
re-warp the stored texture in between using updated landmarks), which trades
away fidelity on fast head motion. Parked at the user's direction.

Related correction: an earlier note dismissed TensorRT fp32 for the enhancer by
comparing it against the *broken fp16* number rather than CUDA. fp32 is ~2x
faster than CUDA and correct -- but adopting it segfaults reproducibly on first
inference on this ORT/TensorRT build. Recorded in FaceEnhancer's docstring as
the biggest available win once the runtime is upgraded.

## Done -- `offline/face_beauty_gpu.py`

`GpuFaceBeautyProcessor` mirrors `pipeline.demosaic.GpuRmProcessor`: frames stay
in device memory from NVDEC to NVENC, all four ONNX graphs read/write GPU
buffers through ORT IOBinding, and every resample is a CuPy kernel written for
this module (letterbox+CHW fused, affine warp, CHW<->crop conversion, parser
argmax, LUT mask, separable Gaussian feather, and a fused affine paste-back that
blends into the frame with no temporaries). `cupyx.scipy.ndimage` does not JIT on
this install (24 compile errors), hence the hand-rolled blur.

`offline/face_beauty.py` gained `convert_clip_gpu` plus `--pipeline
auto|gpu|ffmpeg`. The ffmpeg path stays for `--segment` (multi-range into one
encoder) and `--max-side` (the GPU path encodes at source resolution), and auto
falls back to it if cupy/PyNvVideoCodec are missing.

Two helpers were factored out of the engine so both paths share one
implementation: `decode_yunet` (the 12-tensor YuNet decode + NMS) and
`retouch_crop` (the whole retouch sequence). The retouch deliberately stays on
the host in both paths -- the crop is a fixed 512x512 regardless of frame size,
so the round trip is ~0.3 ms while a GPU version needs a hand-written LAB
conversion.

### Verified

GPU vs CPU on the same frames: **PSNR ~72 dB, max channel diff 7, zero pixels
differing by more than 8** -- i.e. bilinear rounding only. Output video is HEVC +
AAC with the source audio.

| source | faces/frame | ffmpeg | GPU | gain |
|---|---|---|---|---|
| 720x1280 | 1 | 5.0 fps | 8.6 fps | 1.7x |
| 4096x2048 | 2 | 2.7 fps | 4.9 fps | 1.8x |
| 7680x3840 | 0 | 1.8 fps | 73.9 fps | 41x |

The 8K row isolates frame transport: the ffmpeg path spends ~550 ms/frame just
moving an 88 MB frame across the process boundary and downscaling it on the CPU,
versus ~13 ms on the GPU path. With faces present the projected 8K gain is ~3.5x
(13 + N*102 ms against 562 + N*102 ms).

## Next: 8K/VR detection is the blocker, not throughput

That 8K clip reports **0 faces at every threshold down to 0.15**, because YuNet's
input is a fixed 640x640 and 7680 -> 640 shrinks a real 119 px face to ~10 px.
Detecting the same eye in 2x2 tiles finds it immediately. So:

1. **Tiled/ROI detection** is required before any VR work is meaningful -- run
   the detector per tile (or on a coarse pass then refine), in eye-local space.
2. Then the RM VR path applies directly: `pipeline/vr_reproject.py` is already
   CuPy and validated pixel-for-pixel against ffmpeg `v360`. Derive yaw/pitch/fov
   from the face box exactly as `demosaic._region_view` does, `to_flat` into the
   aligned crop, and `blend_into` back with a feathered alpha. The affine face
   warp assumes a perspective view, so this is needed for correctness near the
   edges, not just for quality.

# Work Handover (2026-08-01, part 4)

## GFPGAN on TensorRT -- the crash was never about fp32

Bisecting the segfault:

  fp32 alone                        ok, 30.3 ms
  fp32 after a CUDA-EP session      ok, 36.4 ms
  fp32 after a TensorRT-EP session  segfault, during the build
  cached fp32 after a TRT session   ok, 29.5 ms

So **building** any TensorRT engine while another TensorRT session is alive
crashes this ORT 1.25.1 / TRT build; **loading** a cached engine is fine.
Consistent with the multi-session GPU thread-safety reports in
onnxruntime#26610 / #16790.

`build_trt` now frees each session before the next (explicit del + gc) and
builds the enhancer last, so the runtime path only ever deserialises. fp16 is
still unusable for this graph (silently darkened output), so the engine is fp32,
cached under `<enhancer>_fp32`. Output is numerically identical to CUDA: PSNR
63.6 dB, max channel difference 1.

Enhancer 55 ms -> 30 ms; end to end 8.6 -> 11.1 fps at 720p, 4.9 -> 5.9 fps at 4K.

## Tiled detection -- 8K/VR went from 0 faces to working

`plan_detection_tiles(width, height, mode)` returns the source windows to detect
over. SBS frames are always split per eye first (one letterbox of the whole
frame would squash both eyes into the same 640 and halve the pixels a face
gets), then each eye is gridded into ~1600 px windows with 25% overlap when its
edge exceeds 2200 px. Tiles never straddle the eye boundary.

  720x1280 flat   ->  1 window
  1920x1080 flat  ->  1 window
  4096x2048 SBS   ->  2 windows (per eye)
  3840x2160 flat  ->  6 windows
  7680x3840 SBS   -> 18 windows

`detect_tiled` runs each window and merges with NMS across tiles.
`--detect-mode auto|full|tiled` and `--detect-interval N` (reuse boxes for N-1
frames; landmarks still update every frame) are exposed on the CLI and in the
tuning dialog's detection group.

Measured on the 7680x3840 clip that previously reported **0 faces at every
threshold down to 0.15**: now **240 faces over 120 frames** (one per eye), at
5.0 fps with interval=1 and 5.7 fps with interval=8. Detection is only ~36 ms of
the frame (18 windows), so the interval matters less than expected -- the two
faces at ~90 ms each dominate. Output verified visually: both eyes restored,
paste-back aligned with no tile-offset artefacts.

For comparison the original ffmpeg CPU path on the same clip was 1.78 fps *and
found nothing*.

# Work Handover (2026-08-01, part 5)

## VR flat reprojection wired in

Each face on an SBS/VR source is now restored through a gnomonic flat view,
mirroring the RM path: derive yaw/pitch/d_fov from the face box exactly as
`demosaic._region_view` does, `to_flat` into a 640 working view, align/restore/
retouch there, then composite back.

Two additions to `pipeline/vr_reproject.py`, both purely additive:

- `flat_to_equirect_blend_masked_u8` / `blend_into_masked`. RM restores the whole
  flat view so its blend writes every pixel of the crop window back; face beauty
  only changes what is inside the face mask, and writing the whole window back
  would re-resample (and soften) the untouched ring around the face. The masked
  variant carries a flat-space alpha plane and multiplies it into the edge
  feather, so alpha-0 pixels are never written.
- `project_points_to_flat`, a host-side twin of the kernel's `project_to_flat`.
  The detector's 5 keypoints are already known in eye-local equirect space, so
  they are projected directly instead of re-running the detector inside the flat
  view. Validated against the GPU forward kernel with a marker test: a marker at
  eye (960,960) lands at flat (256.31, 256.31) with the actual blob centroid
  0.5 px away.

`GpuFaceBeautyProcessor._restore_into` is now shared by the direct and VR paths;
the VR path additionally records the face mask into the flat alpha plane.
Failure at any step falls back to the direct warp.

## When it actually matters: pitch, not yaw

Measuring the distortion a similarity transform *cannot* undo (so the enhancer
receives a bent face), in units of its 512 input, by taking a real face's
keypoints and rigidly moving them around the sphere:

  yaw 0..75, pitch 0    0.04 px      <- no distortion anywhere along the horizon
  pitch 20             3.2 px
  pitch 40            18.4 px
  pitch 60            58.1 px
  pitch 75           108.8 px
  yaw 30 / pitch 30    9.6 px
  yaw 45 / pitch 45   24.7 px

That is the expected equirect behaviour -- longitude is linear along the equator
and compressed by cos(lat) away from it -- and it means the direct warp is exact
for any face near eye level and degrades only with elevation. On the real 8K
clip both faces sit ~7 deg off centre, so vr on/off differ by a mean of only
1.16/255; the correction is insurance for faces high or low in frame.

Cost is ~4% (342 -> 355 ms/frame at 8K). `--vr-reproject auto|on|off` (auto = SBS
sources) is on the CLI and in the tuning dialog.

# Work Handover (2026-08-01, part 6)

## Two measurement corrections

Profiling the GPU pipeline with CUDA-synchronised stage timers overturned two
things recorded earlier:

1. **"The parser costs 42 ms."** That number was the *CPU preprocessing* inside
   `FaceParser.parse` (cv2.resize + ImageNet normalise + transpose), not
   inference. Through IOBinding the parser runs in **1.3 ms**. Swapping to
   bisenet_resnet_18 would have been pointless.
2. **"Keep the retouch on the host, the transfer is only 0.3 ms."** The transfer
   is indeed cheap (~2 ms); the *arithmetic* was 74 ms of a 116 ms frame at 720p.
   Conflating the two was the mistake.

Consequently the earlier "112 ms inference floor, realtime impossible" verdict
was wrong. The real floor at 720p was 48.8 ms, and is now much lower.

## Done

### Retouch moved to the GPU (`offline/face_beauty_retouch_gpu.py`)

Bilateral (half-res, fixed kernel), an sRGB<->Lab round trip following OpenCV's
8-bit convention, and unsharp-mask sharpening, all as CuPy kernels; the tonal
passes accumulate per channel exactly like the host version. **74 ms -> 1.34 ms**
(skin smooth 0.04, lab passes 1.03, sharpen 0.04, four masks 0.23). CPU/GPU
parity holds at PSNR 67 dB, max channel difference 8.

### GPEN restorers added, with per-model templates

`gpen_bfr_256` aligns to **arcface_128**, not ffhq_512, so the template now
travels with the model entry (`WARP_TEMPLATES`). The working crop stays a fixed
`CROP_SIZE` 512 -- the parser's input is fixed at 512 and masks/retouch/paste are
sized from it -- and only the enhancer's own tensor is built at its native
resolution, so a 256 restorer really does run at 256.

Measured on one crop, TensorRT fp32: gpen_bfr_256 **6.10 ms**, gfpgan_1.4
**37.95 ms**, restoreformer++ **130.13 ms**. Visual quality of gpen_bfr_256 is
competitive with gfpgan_1.4 (sharp eyes and teeth; a slightly higher-contrast
look, not a worse one).

**Licence:** github.com/yangxy/GPEN ships **no LICENSE file at all** -- the GitHub
API reports no licence, so no rights are granted by default -- and its README
states the 2048 model was withdrawn and the published weights are "not our best
model due to commercial issues". Acceptable for this non-commercial open-source
build, which downloads weights at runtime; **do not bundle these .onnx files into
a redistributed package**.

## Where the time goes now (720p, 1 face, gfpgan)

  landmark              4.56 ms
  detect (1 window)     2.59 ms
  parser inference      1.30 ms
  retouch (all passes)  1.34 ms
  warp/paste/masks     <0.40 ms
  measured frame       42.03 ms

## Model picker moved onto the page

Restoration model is now chosen on the page itself (both tabs, kept in lockstep
like the preset) rather than inside the tuning dialog, with the measured cost in
each label and a download state beside it:

  GPEN 256 - fastest (~6ms)        GFPGAN 1.4 - slower (~38ms)
  GPEN 512 - fast (~31ms)          RestoreFormer++ - slowest (~130ms)

A "Download" button appears only when the selected model is missing and fetches
just that file. The mirror handling already existed -- `hf_download.hf_endpoints`
puts hf-mirror.com first when the UI language is zh -- so nothing was needed
there. Default model for a fresh install is now gpen_bfr_256.

## Three real defects found while wiring this up

1. **Truncated downloads were promoted to the real filename.** A stream that ends
   early ends *cleanly*, so `download_file` renamed the `.part` anyway; the
   corruption only surfaced later as "Protobuf parsing failed". It now compares
   the received byte count against Content-Length before renaming. Hit this for
   real: gpen_bfr_512 arrived as 6 MB of a 284 MB file from hf-mirror.

2. **A crashed engine build left a partial `.engine`, and `trt_engine_cached`
   counted any `.engine` as valid** -- so the runtime happily loaded a corrupt
   engine and segfaulted. Builds now write a `build.ok` marker only after the
   engine has been built *and* run once, and the cache check requires it.
   Existing caches lack the marker and rebuild once.

3. **Engine builds could happen on the runtime path.** Constructing a model with
   `provider="trt"` when its engine was missing built it inline. New
   `runtime_provider()` downgrades to CUDA in that case and logs it, so the rule
   is now "cached engine or CUDA, never build inline"; `build_trt_stage` opts out
   via `force_trt` because building is its job.

`build_trt` also spawns **one subprocess per engine** now and re-emits the
child's output (the TensorRT dialog parses it for progress). Freeing the Python
objects was not enough on its own.

## gpen_bfr_512 is not validated

It benchmarked at 30.97 ms in a clean process earlier, but its engine build now
crashes on the verification inference on this machine. The engine file itself
