## 一、最重要：CUDA 主上下文必须在进程启动时抢到 blocking-sync 标志

计划里完全没有这一项，但它是整条通道能不能跑的前提。

NR 引擎通过 CUDA↔D3D12 interop 拿画面，而它**拒绝**在主上下文（primary context）
没有 FFmpeg 那套 blocking-sync 调度标志时建立 interop：

```
DLSS5 process_cuda_v6 failed: NR pass 1/1 failed:
CUDA interop unavailable: active CUDA primary context does not use FFmpeg blocking-sync flags
```

引擎自己会调 `cuDevicePrimaryCtxSetFlags(blocking sync)`，但这个调用在上下文**已激活**
后返回 `708 CUDA_ERROR_PRIMARY_CONTEXT_ACTIVE`，无法补救。实测：

| 顺序 | primary ctx flags | 结果 |
|---|---|---|
| `BRIDGE.initialize()` 在前，cupy 在后 | 4 (BLOCKING_SYNC) | **OK** |
| cupy 先分配，再 `BRIDGE.initialize()` | 0 | **每帧失败** |
| cupy 先分配，再手动 `SetFlags` | 0（返回 708） | **每帧失败** |
| 进程一开始就 `cuInit` + `SetFlags`，之后随便用 | 4 | **OK** |

离线路径当初"跑通"纯属顺序侥幸：`offline/dlss5_offline.py` 在第一次 cupy 分配**之前**
构造 `DLSS5Stage`。服务进程里 cupy / PyNvVideoCodec / TensorRT 都会先建上下文，所以
照搬必然失败。

**做法**：`utils/dlss5.prepare_cuda_context_for_dlss5()` —— 只做 `cuInit` +
`cuDevicePrimaryCtxSetFlags`，不碰任何 DLSS5 DLL，在 `main.py` 的
`configure_gpu_runtime_cache()` 之后、`setup()` 之前调用（`config.DLSS5_ENABLED` 为真时）。
没有部署 runtime 的机器只多花几毫秒。`cuda_context_ready()` 是它的结果，
`source_block_reason_dlss5(realtime=True)` 会读它并给出 `dlss5_cuda_context_unprepared`。

> 往 `main.py` 里加任何新的 GPU 初始化时，**不要**排到这个调用前面。

另外，计划 §2.4 担心的"每帧重建 NGX feature"**不存在**。实测 3840×1920、30 帧：

| stream 方案 | 首帧 ms | 稳态中位 ms |
|---|---|---|
| null stream（冷启动） | 587.95 | 29.25 |
| null stream（已热） | 29.25 | 29.54 |
| 一条固定非 null stream | 29.22 | 29.49 |
| **每帧新建一条 stream** | 29.59 | 29.56 |

即 feature 只建一次（~590ms），引擎不按 stream 做会话 key。不需要 `utils/rtx_vsr.py`
那套修复。

## 二、fps × 分辨率表（计划 §6.1 要求的那张）

**NR 单阶段**（RTX 5060 Ti，不含解码/编码）：

| 分辨率 | 尺寸 | 首帧 ms | 稳态中位 ms | fps |
|---|---|---|---|---|
| 1080p | 1920×1080 | 560.6 | 10.0 | 100.0 |
| 2.5K | 2880×1440 | 504.5 | 18.0 | 55.5 |
| 4K VR | 3840×1920 | 501.9 | 30.4 | 32.9 |
| 4K 2D | 3840×2160 | 496.5 | 34.4 | 29.1 |
| 6K VR | 5760×2880 | 619.4 | 69.9 | 14.3 |
| 8K VR | 7680×3840 | 805.1 | 127.4 | 7.9 |

**端到端**（真实 seek 帧生成器：解码 → NR → NVENC，扣掉 ~1.9s setup 后的稳态）：

| 源 | 尺寸 | 稳态 fps | 像素率 |
|---|---|---|---|
| dance_..._4K.mp4 | 1216×2160 | ~78 | 205 Mpix/s |
| vr4k_8bit | 3840×1920 | ~31.9 | 235 Mpix/s |
| flat4k_8bit | 3840×2160 | ~28.3 | 235 Mpix/s |

结论：这条链能稳住 **~230 Mpixel/s**。所以门控是两层，都在
`utils/dlss5.source_block_reason_dlss5(realtime=True)` 里：

1. **分辨率上限** `DLSS5_INPUT_MAX_HEIGHT=2160` / `DLSS5_INPUT_MAX_WIDTH=4096`
   → 6K/8K 只走离线（`dlss5_source_too_large`）。
2. **像素率预算** `DLSS5_REALTIME_PIXEL_RATE=200_000_000`，判据 `宽×高×源fps`
   → 同样是 4K，24fps 能播、60fps 不能（`dlss5_source_too_fast`）。换更快的卡改这一个
   环境变量即可，设 0 关掉这层检查。

DLNA 列表（`_dlss5_dlna_enabled`）读的是索引里的 `fps`，路由读的是 probe 的
`timing.source_fps`，**同一个函数**，所以不会出现"目录里列了、点开 409"。

离线路径同分辨率只有 12.9 fps（4K VR），因为它每帧 `d_out_y.get()` 回主机再喂 NVENC；
实时通道全程 GPU 驻留，快 2.5 倍。计划 §5.2 说的就是这件事。

## 三、参数默认值原先是错的

`config.py` 里 DLSS5_* 原本整块清零。但 NR 每个控制项的**中性值**不是 0：

| 控制项 | 范围 | 中性值 | 原默认 |
|---|---|---|---|
| intensity | 0.00–2.00 | 1.00 | 0.5 |
| local_tone | 0.00–2.00 | 1.00 | 0.0 |
| local_structure | 0.00–2.00 | 1.00 | 0.0 |
| **skin_structure** | **-1.00–2.00** | **-1.00** | 0.0 |
| color_strength | 0.00–1.00 | 1.00 | 0.0 |
| tone_preservation | 0.00–1.00 | 0.00 | 0.0 |
| face_skin_protection | 0.00–1.00 | 0.00 | 0.0 |
| grain_preservation | 0.00–1.00 | 0.00 | 0.0 |
| shimmer_suppression | 0.00–1.00 | 0.70（视频） | 0.0 |
| nr_passes | 1–4 | 1 | 1 |
| style | 0/1/2 = 默认/自然/电影感 | 0 | 0 |

（来源：`reference/dlss5-visual-enhancer-main/README.md` 的参数表与
`src/live/models.py` 的默认值。）

清零意味着"完全不做色彩处理"，而 `skin_structure=0.0` 高于原生 -1.00，会被读成一次
**刻意的**肤质调整（该值是否高于 -1.00 正是决定要不要开 automatic mask 的依据）。
已按上表对齐 `config.py` / `DLSS5Settings` / `ui/settings.py DEFAULTS` 三处。
范围表放在 `utils/dlss5.DLSS5_RANGES`，UI 滑块直接读它，**不可能**再滑出运行时拒绝的值。

`shimmer_suppression` 在参考实现里有两条路径：host 路径用 Python 光流自己做、把 DLL
字段清零；CUDA 路径交给引擎。我们是 CUDA 路径，所以 0.70 直接传给引擎有效。

## 四、通道本体（照 SuperRes 改的部分，按计划执行，无意外）

- **`pipeline/pynv_stream.py`**：`SEEK_FRAME_MODES` 加 `dlss5`。原来两处各自 `new
  SuperResStage(...)` 的构造点合并成一个 **`make_frame_stage(mode, ...)`**，live worker
  和 seek 帧生成器都走它；`seek=True` 区分 SuperRes 的目标分辨率。计划 §2.1 提醒的
  "保持 N 份同步"的坑现在结构上不存在了。`tests/test_rtx_vsr.py` 里那条守护测试已改成
  守护新的不变量。
- **`pipeline/dlss5_stage.py`**：补 `output_size` 和 `process(frame, index)`
  （与 `SuperResStage` 同形），带 NVENC ring；`reset` 每个 stage 只置一次（一个 stage
  就是一次 seek/live 会话，首帧必然是切换点）。构造时就调
  `source_block_reason_dlss5`，10-bit 源在构造期被拒而不是跑到第一帧才炸。
  顺便去掉了模块顶层的 `configure_gpu_runtime_cache()` 副作用（计划 §5.5）。
- **`http_app/routes_media.py`**：`_SEEK_ROUTE_MODES`、`_seek_output_mode`、
  `_configured_passthrough_modes` 加 `dlss5`。五处 superres 的 409 守卫收敛成
  `_enhanced_mode_block_reason(path, mode, meta)` 一个入口。
  `_vmp4_slot_output_size` 给 dlss5 加了**显式**分支返回源尺寸——stage 从源尺寸工作、
  看不到 `DECODE_MAX_SIDE`，走默认分支会让 MP4 外壳声明被裁过的尺寸。
  帧预算（`_vmp4_frames_frame_budget` / `_vmp4_frames_source_budget`）按计划**不动**：
  1x 输出继承源码率预算是对的。
- **`dlna/content_directory.py`**：独立前缀 `pldn_` / `pldn_item_` / `sdn_`，时间索引
  token `d`；标题固定 `[DLSS5]`，**不带任何参数**（Skybox 会缓存文件名）；
  `_seek_supported_mode("dlss5")` 恒 True；分辨率走默认分支（1x）。
  `_id_to_live` 里 `pldn_item_` 必须排在 `pldn_` 前面判断，否则前缀互吃。
- **UI**：`DLSS5SettingsDialog`（style / nr_passes / intensity / shimmer 主控件，
  其余 7 项进"高级参数"折叠区 + auto_mask），接了 `NgxDriverNotice(dlss5_runtimes())`
  → 驱动低于 615.00 或非 RTX 50 时自动提示。`PlaybackModeChooser` 常显（1x 恒可虚拟
  文件播放，不像 SuperRes 要联动）。仪表盘加 `[DLSS5]` 卡片，用新画的 `dlss5` 图标
  （SuperRes 那个图标画的是"放大"，语义不对）。**runtime 不存在时卡片直接不显示**。
  三语 `dlss5.*` 键已加（UTF-8 BOM，按 `superres.performance_note` 之后插入，未重排）。

### 实测通过

- seek 帧生成器 `output_mode="dlss5"`：200 帧真实 access unit，1216×2160 稳态 ~78fps。
- DLNA 列表真的出现 `[DLSS5]dance_..._4K` 虚拟文件，
  url `...mp4.dlss5.seek.mp4?mode=dlss5&ptv=11`，object id `sdn_...`，

- 离线 `--engine dlss5` 跑通，PSNR vs 源 29.6dB（色度 39/43dB，无偏色），画面
  纹理/对比明显增强。

## 五、顺手修掉的既有 bug

1. **`offline/dlss5_offline.py` 没有 `import numpy as np`** —— 第一帧就 NameError。
   该文件从未被真正跑过。
2. **同文件把 `PASSTHROUGH_PYNV_PRESET`（PyNv 拼法 `"P1"`，大写）直接交给 ffmpeg 的
   `hevc_nvenc`**，后者只认小写，报 `Error applying encoder options: Invalid argument`
   然后退出，调用方在下一帧收到一个什么都没说的 `[Errno 22] Invalid argument`。
   已按 `offline/rtx_vsr.py` 的做法归一化，并把编码器 stderr 收集起来、
   在它提前退出时给出真正的原因。
3. **`routes_media.py` 的 SuperRes pseudo-VOD 守卫**
   `_, superres_meta = await asyncio.to_thread(_probe_live_request_metadata, path)`
   用 2 元解包接 3 元返回值，必然 ValueError，被外层 `except` 吞成
   "metadata probe failed"。两处都已改正。

## 六、已知限制 / 下一步

- **10-bit / HDR**：`realtime=True` 直接拒 10-bit（`dlss5_10bit_unsupported`），
  因为 kernel 写死 8-bit BT.709 limited range。要支持得接 P010
  （bridge 里 `FORMAT_P010=3` 已定义，未接）。计划 §5.4 仍然成立。
- **色彩空间**：kernel 仍写死 BT.709 limited range，SD（BT.601）/ full range 源会偏色。
  计划 §5.3 未做。实测 BT.709 源色度 PSNR 39/43dB，无偏色，所以优先级不高，但 SD 源要注意。
