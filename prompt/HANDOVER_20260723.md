# Work Handover (2026-07-23)

## Request

Offline mosaic restoration (RM) hangs with no progress on some videos while
others succeed. Repro: a 4096x2048 H.264 VR180 SBS sample, start at 4:00 for a
1-minute clip. It freezes at ~200 output frames.

## Root Cause (confirmed by 4 probes)

The restorer ONNX model (`vr_mosaic_restoration_chunk_model_v0.1.onnx`) runs with
a **dynamic `batch` dimension == the number of mosaic regions detected in the
frame**. The TensorRT EP was configured with `trt_engine_cache_enable` but **no
fixed optimization profile**, so ORT-TRT locks each engine to the first shape it
sees and rebuilds a new engine at runtime for every previously-unseen region
count.

- Engines for batch 1..4 were already cached from earlier videos (load in <0.1s).
- This clip is the first to detect **5 regions (batch=5)** ~13s in, forcing a
  fresh runtime TRT engine build. That build stalls under VRAM pressure (NVDEC
  ThreadedDecoder + NVENC + CuPy pool + existing engines all resident) and never
  returns, freezing the whole pipeline. Same "VRAM-exhaustion -> hang" class as
  the earlier NVDS finding.
- This is why "some videos work, some hang": it depends on whether a video hits a
  region count that has never been cached.

Evidence chain:
1. Decode-only (`PyNvThreadedSerialDecoder`, same seek): 3596 frames in 8.2s ->
   decode is innocent.
2. `faulthandler` all-thread dumps every 30s for 5 min: main thread permanently
   in `demosaic.py` `run_with_iobinding` (restorer inference).
3. Per-chunk batch logging: batch=3/4 each ~0.07s; the first batch=5 never
   returns.
4. `--provider cuda` (no TRT engine build): batch=5 runs at 0.4-1.0s and the clip
   completes (RC=0) -> the model math is fine; the hang is TensorRT-specific.

All three restorer inputs (`lqs`, `prev_ds`, `states`) have a dynamic `batch`
axis.

## Done

1. `pipeline/demosaic.py`:
   - Added `_restorer_trt_profiles(max_batch)` producing
     `trt_profile_min/opt/max_shapes` for all three inputs (min=1, opt=4,
     max=`RM_MAX_REGIONS`). One engine now covers the whole region-count range;
     no runtime rebuilds.
   - `_onnx_providers()` / `_make_session()` gained an optional `trt_profiles`
     argument applied only to the restorer session (detector unaffected).
   - `DemosaicRestorer.__init__` passes the profile.
   - `_postprocess_detections()` gained a `max_det` parameter (top-N by score
     after NMS); both call sites (realtime `detect_blob` and GPU
     `_run_detector_gpu`) pass `config.RM_MAX_REGIONS` so the batch can never
     exceed the profiled max.
2. `config.py`: added `RM_MAX_REGIONS` (default 16, env `PT_RM_MAX_REGIONS`).

All new parameters are optional and backward-compatible. The same fix also covers
the realtime [RM] DLNA path (shared `GpuRmProcessor`).

## Verification

- Full TRT pipeline on the previously-hanging clip: batch=5 chunks now run in
  0.07-0.16s (no rebuild); the clip completes fully — 1498 frames, 63.2 fps avg,
  RC=0.
- `--provider cuda` control run also completes (RC=0), confirming the model is
  correct and the original hang was the TRT shape rebuild.
- Import/profile sanity check passes; profile strings verified for
  `lqs/prev_ds/states` at batch 1/4/16.

## Follow-up

- First run after this change rebuilds the profiled restorer engine (covering
  1..16) once during warmup — a few minutes; cached and instant afterwards. Old
  per-shape `.engine` files are ignored (profile changes the cache hash), so no
  manual cleanup of `runtime_cache/demosaic_trt/restoration_chunk` is needed.
- Frames with >16 regions restore only the top-16 by score (extremely rare in
  practice); raise `PT_RM_MAX_REGIONS` if ever needed, at the cost of a wider
  profile / more VRAM.
- Consider verifying realtime [RM] DLNA playback on a clip that reaches high
  region counts to confirm the shared-path fix end to end.
