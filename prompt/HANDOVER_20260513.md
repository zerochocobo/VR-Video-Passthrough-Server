## Alpha passthrough subtitle alpha-mask contamination fix

- User reported that when subtitles appear in alpha passthrough video, the original red-channel alpha image becomes the subtitle color and passthrough fails.
- Root cause:
  - subtitles were correctly being blended into the source frame before fisheye alpha packing;
  - however, `overlay_alpha_packer_layout` only wrote alpha layout pixels when `mask != 0`;
  - for `mask == 0`, the kernel returned early and left the already projected visible image underneath;
  - when subtitles overlapped those six alpha layout blocks, their color remained in the alpha control area.
- Updated `pipeline/alpha_packer.py`:
  - alpha layout blocks now always write a clean black / neutral-UV base;
  - nonzero mask pixels still write the red alpha value;
  - this prevents subtitle color from leaking into the red alpha-control regions.
- Retained the previous alpha subtitle flow:
  - blend the v360-projected subtitle into the uploaded source NV12 before fisheye packing;
  - merge subtitle alpha into the alpha mask so subtitle pixels remain opaque to the player.
- Verification:
  - `python -m unittest tests.test_alpha_packer` passed;
  - `python -m py_compile pipeline\alpha_packer.py pipeline\pynv_stream.py` passed;
  - `git diff --check` passed.
- Runtime verification needed:
  - retest alpha live playback with same-stem `.srt` / `.ass`;
  - confirm alpha mask blocks remain red/black and no longer show subtitle color.

### Correction after runtime retest

- User reported the first attempted fix was wrong:
  - subtitle color still polluted the alpha control channel;
  - clearing `mask == 0` alpha layout pixels made the six alpha blocks visibly opaque and covered fisheye corners.
- Corrected the design:
  - keep subtitles out of the uploaded source NV12 used by alpha projection;
  - project the clean source frame first;
  - blend subtitle color only onto the projected fisheye visible layer;
  - merge subtitle opacity into the separate `fisheye_alpha` layer;
  - write the six-block red alpha layout from `fisheye_alpha` after subtitle blending;
  - leave alpha layout pixels unchanged when `mask == 0`, matching the original non-opaque behavior.
- Updated `pipeline/alpha_packer.py`:
  - added a projected subtitle blend kernel that maps subtitle overlay coordinates through the same fisheye transform;
  - the kernel skips the six alpha layout regions so subtitle color cannot write into alpha control blocks;
  - subtitle alpha updates `fisheye_alpha`, so subtitle pixels can still be opaque in the player.
- Updated `pipeline/pynv_stream.py`:
  - alpha mode now passes positioned subtitle overlays to `AlphaPacker`;
  - it no longer blends subtitle color into the uploaded source NV12 before alpha packing.
- Verification:
  - `.venv\Scripts\python.exe -m unittest tests.test_alpha_packer` passed;
  - `.venv\Scripts\python.exe -m py_compile pipeline\alpha_packer.py pipeline\pynv_stream.py` passed.

## Startup hardware detection and cold-start UX

- Add a startup-time hardware detection and first cold-start experience across backend and UI.
- Main backend changes are in `main.py`, `utils/gpu_runtime_cache.py`, and `utils/startup_status.py`.
- `utils/gpu_runtime_cache.py` now exposes `predict_warmup_state()` and `ColdStartReport`:
  - reads the warmup marker without triggering warmup itself;
  - probes GPU name, compute capability, driver version, and ONNX Runtime version;
  - classifies Blackwell-class `sm_120+` plus older ORT as a "known slow" combo;
  - returns an ETA bucket and reason such as `cache_hit`, `marker_missing`, `key_changed`, or `inspect_failed`.
- `main.py` now:
  - calls `predict_warmup_state()` before the actual warmup;
  - publishes structured startup state fields to `/status`;
  - reports step/progress/ETA metadata for the warmup phases;
  - delays briefly on failure so the UI poller can read the terminal `failed` state before the local status endpoint is torn down;
  - resets per-step progress once warmup is finished.
- `utils/startup_status.py` now stores structured fields in the local startup state:
  - `step`, `step_index`, `step_total`, `progress`, `eta_sec`, `elapsed_sec`;
  - `cold`, `is_known_slow`;
  - `gpu_name`, `compute_capability`, `driver_version`, `onnxruntime_version`;
  - `reason`, `detail`.
- UI changes are centered in `ui/main_window.py` plus new helpers:
  - `ui/services/startup_status_poller.py` polls `http://127.0.0.1:8299/status`;
  - `ui/widgets/startup_overlay.py` shows a non-modal startup dialog with progress, ETA, details, cancel, and copy-report actions;
  - `ui/diagnostics.py` builds a copyable hardware/report blob that includes GPU probes, runtime versions, warmup marker contents, startup status, and the tail of `server.log`.
- The window now opens the overlay during server startup, updates it from the poller, and closes it when the server reaches a ready state.
- The translations in `ui/translations/en_US.json`, `ja_JP.json`, and `zh_CN.json` were extended for the new startup overlay strings.
- Test coverage added in `tests/test_predict_warmup_state.py` for:
  - known-slow detection;
  - cold-start prediction with and without marker JSON;
  - structured startup status storage/reset behavior.
