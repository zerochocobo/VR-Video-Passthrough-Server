# Handover 2026-05-16

## MKV Cues Risk Handling

- Added lightweight MKV Cues placement detection in `utils/mkv_cues.py`.
- The detector reads only the file prefix and parses EBML Segment/SeekHead/Cues structure instead of running expensive `ffprobe` trace output.
- A test file `videos/test_mkv_8k.mkv` was detected as `tail`, with Cues around byte `10151483952`, so it is considered unsafe for live passthrough.
- Media index schema was upgraded from version 1 to 2 with additive migration only:
  - `mkv_cues_status`
  - `mkv_cues_position`
  - `mkv_cues_reason`
- Existing SQLite cache rows are preserved. For old MKV rows with empty Cues status, the directory cache path forces a re-probe so upgraded users do not keep stale passthrough entries.
- DLNA listing now marks unsafe MKV originals with `[FIX]` or `[需修复]` depending on `PT_UI_LANGUAGE` / system locale, and hides green/alpha passthrough entries for those files.
- UI settings now pass `PT_UI_LANGUAGE` into the server environment.
- Direct `/passthrough_live/...` requests for unsafe MKV are rejected with HTTP 409 to avoid old client URLs entering the PyNv live path.

## MKV PyNv SimpleDecoder Stuck Mitigation

- Reviewed expert notes appended to `summary/summary_20260516_MKV_PYNV_SIMPLEDECODER_STUCK_ISSUE_CN.md`.
- Accepted the low-risk immediate mitigations:
  - `PT_PASSTHROUGH_MKV_LIVE_POLICY` now defaults to `block`, so MKV live passthrough entries are hidden/rejected unless explicitly enabled for diagnostics.
  - `PyNvPassthroughStream.close()` no longer calls `SimpleDecoder.stop()` or performs a second worker join after the worker already failed the first close join. The PyNv binding exposes `stop()`, but the wrapped native object is not reliable here, and the extra wait only delays request cleanup.
- Kept the existing taint marker and stuck-thread stack logging. If a worker remains alive, the process still logs tainted state and should be restarted before continuing alpha passthrough.
- Deferred larger ThreadedDecoder/sequential decode work; that remains the likely next engineering direction but needs a focused implementation and validation pass.

## DLNA External Subtitle P0

- Implemented Phase 1/P0 from `summary/summary_20260516_IMPL_PLAN_DLNA_SUBTITLE_20260516.md` for regular non-live MP4 playback.
- Added `utils/subtitles.py` to discover same-directory external subtitle files for `.mp4`/`.m4v` sources:
  - `movie.srt`, `movie.ass`, `movie.vtt`, `movie.ssa`
  - language-tagged variants such as `movie.zh.srt`, `movie.eng.srt`, `movie.zh.ass`
  - default ordering: untagged, Chinese, English, other.
- Added `/subs/{name}` GET/HEAD in `http_app/routes_media.py` with byte Range support, inline disposition, CORS `*`, and subtitle MIME types.
- Added `CaptionInfo.sec` and `getCaptionInfo.sec` headers to `/media/{name}` GET/HEAD when an external subtitle is found.
- Added DIDL subtitle metadata in `dlna/content_directory.py`:
  - SEC namespace on DIDL root.
  - Extra subtitle `<res protocolInfo="http-get:*:application/x-subrip:*">` entries.
  - `sec:CaptionInfoEx` and `sec:CaptionInfo` nodes.
- This phase does not remux or modify MP4 bytes. It is meant for real-device compatibility testing first.
