# Work Handover (2026-08-02)

## Request

Investigate severe regressions in the new DLNA FaceBeauty entry and the newly
exposed VR RM entry. On VR playback the client showed Alpha output, and every
selected chapter appeared to start from 00:00.

## Evidence and root cause

`debug_output/server.log` and
`debug_output/request_history/request_history_20260802.jsonl` show the exact
fallback chain:

- SKYBOX requested a VR chapter with `mode=rm` and the correct non-zero `t`.
- `dlna/content_directory.py` offered RM for VR, but
  `http_app/routes_media.py::_rm_live_block_reason` still rejected every VR
  source as 2D-only and returned HTTP 409.
- SKYBOX then retried the same media URL without both `mode` and `t`.
- The server consequently selected its default Alpha mode at `0.00s`.

So Alpha/00:00 was not produced by RM itself and seek was not lost inside the
decoder. It was the player's fallback after contradictory DLNA listing and HTTP
playback gates.

FaceBeauty had a separate cold-start failure. Its first request spent about 39
seconds loading four cached ORT/TensorRT sessions. The generic live first-chunk
timeout was 30 seconds, so the route stopped the stream just as initialization
finished and returned HTTP 504 with zero frames emitted.

## Changes

- Removed the stale 2D-only check from `_rm_live_block_reason`; VR RM is now
  accepted when the source is eligible for the PyNv GPU path, matching the DLNA
  directory gate and the actual `GpuRmProcessor` VR reprojection capability.
- Added a FaceBeauty playback gate matching its DLNA visibility: runtime feature
  must be enabled and the source must be eligible for the PyNv GPU path.
- Added `PT_FACE_BEAUTY_LIVE_FIRST_CHUNK_TIMEOUT_SEC` (default 90 seconds).
  Only FaceBeauty uses this longer cold-start allowance; other live modes keep
  the existing generic timeout.
- Added regression tests for VR RM acceptance, FaceBeauty gating, the
  mode-specific cold-start timeout, and RM/FaceBeauty time-index URLs retaining
  both `t` and `mode`.

## Verification

- Targeted route/content-directory suite: **92 passed + 5 subtests**.
- Full first-party suite (`tests/`), with JSONL persistence disabled only in the
  test process because the running server held today's history file open:
  **532 passed, 2 skipped + 67 subtests**.
- A root-level unscoped `pytest` is not a valid project run here because it also
  collects third-party `reference/` sources and `runtime_cache/` contents.
- Real SKYBOX/GPU playback still needs an application restart and device-side
  retest; expected log signature is `mode=rm` or `mode=face_beauty` with the
  selected non-zero start time, with no immediate 409/504 fallback to a request
  lacking `mode`.

## Workspace note

`TensorrtExecutionProvider_cache_sm120.timing` was already untracked and was not
modified. The initial RM gate edit in `http_app/routes_media.py` was already
present as an uncommitted workspace change when this investigation began; it was
validated, retained, and covered by tests.

# Work Handover (2026-08-02, part 2)

## Request

1. Hide the DLNA SuperRes entry for 8K VR sources.
2. Deeply investigate and improve realtime FaceBeauty FPS.

## SuperRes

The DLNA directory now hides SuperRes for VR sources wider than 4096 pixels
(7680x3840 and 8192x4096), while retaining 4K VR such as 4096x2048. The HTTP
playback/seek gate independently rejects a stale/direct 8K VR SuperRes URL, so a
client cannot bypass the directory policy.

## FaceBeauty findings

Three realtime integration decisions, rather than GPEN itself, were limiting
throughput:

1. The FaceBeauty worker ignored the DLNA `max_fps` cap. A 59.94fps 8K source
   was decoded, processed and encoded at 59.94fps even though the response
   advertised 40fps. This caused permanent under-speed and a mismatched timeline.
2. 2DFAN4 landmark refinement ran for every face on every frame. Real-video
   ablation on a 1920x1080 two-face segment measured **25.1fps** at full settings
   and **45.6fps** with only the landmarker disabled, making it the dominant cost.
3. Realtime inherited the offline default of unlimited faces; cost scales almost
   linearly per face.

## FaceBeauty changes

- The worker now obeys the selected live FPS cap and maps output indices back to
  source indices with `cfr_source_index`, preserving seek while dropping excess
  59.94fps source frames for a 40fps live stream.
- New `BeautyOptions.landmark_interval`. Realtime defaults to 2: run 2DFAN4 on
  alternating frames and reuse the stable refined 5-point alignment between
  updates. Direct and VR-flat paths both cache/reuse their appropriate landmarks.
- Realtime defaults to at most two faces for both 2D and SBS VR. This preserves
  normal two-person shots and both VR eyes; environment overrides can choose 1
  for maximum speed or 0 for unlimited.
- New environment controls:
  `PT_FACE_BEAUTY_LANDMARK_INTERVAL`, `PT_FACE_BEAUTY_MAX_FACES_2D`, and
  `PT_FACE_BEAUTY_MAX_FACES_VR`.
- Offline CLI gained `--landmark-interval` for repeatable quality/performance
  experiments; its default remains every frame.

## Measured result

Actual 1920x1080, two faces per frame, GPEN 256 + parser + all standard retouch:

- old full path: **25.13fps**
- landmarker off (diagnostic only): **45.61fps**
- new interval=2, both faces retained: **37.27fps** (**+48%**)
- new interval=2, max_faces=1 optional extreme: **55.75fps**

Actual 8192x4096 SBS VR stable-state NVDEC -> FaceBeauty core, max two faces:

- old landmarker every frame: **49.08fps**
- new interval=2: **58.97fps** (**+20%**)

With the live worker now correctly capped at 40fps, the measured 8K core has
substantial headroom instead of trying and failing to chase the source's 59.94fps.
The first 8K frames remain slower because they include seek and the initial
18-window full-grid detection; ROI following then becomes the stable state.

## Verification

- Focused tests: **110 passed + 5 subtests**.
- Full first-party suite: **536 passed, 2 skipped + 67 subtests**.
- Added regression coverage for the 8K VR SuperRes policy, landmark interval
  reuse, and 59.94 -> 40fps CFR seek/frame mapping.

# Work Handover (2026-08-02, part 3)

## 2D FaceBeauty ghost-face diagnosis

The reported ghost face was reproduced in `START-595-C.mp4` at about 53.45s.
The source shows the young woman on the right turned almost completely away,
with her visible face area covered by hair. The old output pasted a newly
generated frontal face onto the hair.

This predates the realtime landmark-interval optimization. The exact false
detection had YuNet score 0.617 but 2DFAN4 landmark score only 0.0975. Its
source aligned crop contained only 1.51% parsed facial pixels, versus 26.56%
for the valid face in the same frame.

The root cause was an unsafe validation order:

1. YuNet occasionally accepted a back-of-head/heavily occluded profile as a
   face and supplied plausible-looking five-point detector landmarks.
2. The low-confidence 2DFAN4 result was rejected, but the pipeline still fell
   back to those detector landmarks and ran the generative GPEN restorer.
3. BiSeNet parsed the **generated** crop afterwards. The synthesized eyes,
   nose and skin therefore created their own valid region mask, allowing the
   hallucinated face to be pasted back.

## Fix

- Both CPU and GPU paths now parse the untouched aligned source crop before
  any blind restoration.
- The final paste mask and all retouch masks come from this source parse, so a
  generated face can no longer validate or expand its own writable region.
- Landmark confidence is retained on each detection. When no parser coverage
  is available, blind restoration requires a 2DFAN4 score of at least 0.20.
- The CPU/offline path also suppresses blind restoration when the source face
  region covers less than 8% of the aligned crop. Non-generative retouch may
  still operate on genuine source facial pixels.
- The GPU path deliberately avoids downloading/reducing the source mask for a
  host branch; doing so introduced a device synchronization and cost several
  FPS. It uses the source mask for composition and the already-host-resident
  landmark score for the cheap generation gate.

No output-video frame dropping was added for this fix. Realtime performance
still comes from running detection/2DFAN4 at configured intervals while every
output frame is decoded, retouched/composited and encoded on its normal CFR
timeline.

## Verification

- The exact 53.45s frame was rerun with detection/landmarks every frame: the
  frontal face on the hair is gone.
- The same frame was rerun with the DLNA realtime settings
  (`detect_interval=2`, `landmark_interval=2`): the ghost face is also gone.
- The difficult 48-56s two-face segment ran at 25.14fps with realtime interval
  settings. This segment is materially heavier than the prior 840s benchmark
  because it contains nearly two accepted detections on every frame.
- Added regression tests for low source-face coverage, low landmark confidence,
  and source-before-enhancer parser ordering.
- Full first-party suite: **539 passed, 2 skipped + 67 subtests**.
