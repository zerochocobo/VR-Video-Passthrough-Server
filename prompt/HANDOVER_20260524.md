## AV sync live Range rollback

- User reported the live Range/seek semantic change made playback completely
  fail.
- Rolled back the first A/B fix that had:
  - added `PT_PASSTHROUGH_LIVE_RANGE_POLICY`;
  - added `PT_PASSTHROUGH_LIVE_ADVERTISE_SEEK`;
  - rejected non-zero `/passthrough_live` Range requests;
  - removed live `TimeSeekRange` / `X-AvailableSeekRange`;
  - changed live `DLNA.ORG_OP` to `00`.

- The external replies still suggest Range/live-seek semantics as a likely
  root cause, but the hard `416`/pure-live change is not viable for the tested
  client. A safer next experiment should be behind a toggle or targeted to a
  specific profile without changing the default playback path.

## AV sync CDS live metadata adjustment

- User provided analysis of the ContentDirectory `res` metadata:
  - live chapter URLs such as `/passthrough_live/...?...t=1080` were advertised
    with `duration`, `bitrate`, `DLNA.ORG_OP=10`, and time-seek flags.
  - This can make a generated live chapter look like a seekable VOD resource
    and may explain the client's later large byte Range requests.
- Adjusted CDS only, leaving the HTTP playback behavior unchanged after the
  failed hard-Range experiment:
  - bumped `_DIDL_SCHEMA_VERSION` from 5 to 6 so clients see a new `ptv`;
  - passthrough live direct items and chapter items now advertise
    `DLNA.ORG_OP=00`;
  - live `res` omits `duration` and `bitrate`;
  - live `res` omits `DLNA.ORG_FLAGS` instead of advertising time-seek flags.
- Added tests covering short live metadata and live chapter `res` metadata.

## AV sync one-GOP video lead root cause

- User argued the large Range requests are likely metadata probing, not the
  playback sync root cause. Rechecked from packet/content evidence instead.
- Fresh local live capture for `videos/urvrsp00566_1_8k.mp4?t=180` still had
  audio start/content aligned to the requested source time within about 21 ms.
- Added video-content verification for green captures:
  - `tools/check_live_video_alignment.py`
  - It extracts one captured frame, masks out green, and matches foreground
    luma against PyNv-decoded source frames around the requested time.
- The old/current running server output failed this video check:
  - expected source frame index near `10789` at 180 s;
  - captured first green frame matched source index `10849`;
  - offset was about `+0.997 s`, exactly one `PT_PASSTHROUGH_GOP=60` at 59.94 fps.
- Isolated root cause with a direct encode/mux probe:
  - raw PyNv HEVC encoded 120 frames correctly;
  - FFmpeg MPEG-TS mux with `-fflags +genpts+nobuffer+flush_packets` output only
    60 video packets and the first decoded frame matched source index `10849`;
  - the same mux without `+nobuffer` output 120 packets and first frame matched
    source index `10789` with about `-0.004 s` content offset.
- Changed default `PT_MUX_NOBUFFER_ENABLE` from `1` to `0`. The helper still
  supports the env switch as a diagnostic override, but comments now warn that
  `+nobuffer` can drop the first GOP from raw HEVC and make video lead audio.
- Updated mux latency/config default tests.
- Validation:

    -> `21 passed`

## Offline MatAnyone2 TensorRT Cache

- User requested offline TensorRT cache support for MatAnyone2 and removal of the RVM balanced/mid-speed choice from the offline UI.
- Model target decision:
  - MatAnyone2 TensorRT build targets `models/matanyone2_onnx_512_bs1/matanyone2_step_update.onnx`.
  - Reason: `step_update` is the per-frame propagation hot path; `image_key`, `mask_memory`, and `first_frame_refine` are bootstrap/segment-reset graphs and remain CUDA.
- Cache separation:
  - `utils/trt_manifest.py` now supports model keys `rvm` and `matanyone2`.
  - RVM cache remains under `runtime_cache/trt_engines`.
  - MatAnyone2 cache uses `runtime_cache/trt_engines/matanyone2_onnx_512_bs1`.
  - Fingerprints are model-aware; MatAnyone2 fingerprints avoid RVM-only input-size/downsample fields.
- UI:
  - moved the TensorRT config dialog into `ui/widgets/trt_cache_dialog.py` for reuse.
  - Home page still opens the RVM TensorRT cache dialog.
  - Offline page now has a TensorRT cache row above `画质速度` for both single and batch tabs.
  - Offline cache row switches status/config target based on selected engine: RVM fast -> RVM cache, MatAnyone2 -> MatAnyone2 cache.
  - Removed `RVM中速` from the offline engine combo while leaving backend support for old CLI/test compatibility.
- Runtime path:
  - `ui.services.trt_warmup_process` accepts `--model matanyone2` and builds the MatAnyone2 `step_update` TensorRT cache.
  - `offline.convert` enables `PT_OFFLINE_MATANYONE2_TRT=1` whenever the MatAnyone2 cache is ready, independent of the live/home TensorRT toggle.
  - `tools/offline_passthrough.py` and `tools/offline_alpha_passthrough.py` only use TensorRT providers for `matanyone2_step_update.onnx`; other MatAnyone2 ONNX sessions stay CUDA/CPU.
