## 虚拟 MP4 实现与剩余实时目录功能调研

用户要求先研究现有虚拟 MP4 的实现，再盘点仍通过实时目录提供的功能。本次只进行代码研究和已有测试验证，未实施功能迁移。调研基于当前工作区，HEAD 为 `d6e0af3`（2026-09-16，`fix cudnn`），开始时工作区无改动。

### 已确认的状态

- 当前 `pipeline/pynv_stream.py::SEEK_FRAME_MODES` 是 `green / alpha / superres / dlss5`。DLSS5 已接入，虽然默认开关、运行时和源视频门控可能让 UI/DLNA 不显示它。
- 默认 VMP4 后端是 `slot_frames`。旧 `slot` 是一个 GOP 一个 MP4 sample，旧 `cache_file` 会依赖离线产物；不能把这些路径等同于当前逐帧实时虚拟文件。
- SuperRes 默认只有 Native（1×）目标提供虚拟文件；放大目标保留实时目录。`PT_RTX_VSR_SEEK_ALLOW_UPSCALE` 可覆盖限制，但这是显式实验开关，不能视为默认支持。
- 仍以实时目录提供的独立功能：Face Beauty、RM、2D→3D（内部模式 `two_dvr`）、SI；另有 SuperRes 非 Native 目标。
- 2D Alpha 是 Alpha 的布局/投影设置，不是需要另外新增的 seek 输出模式。

### 实现骨架

1. `dlna/content_directory.py::_video_items()` 对支持 seek 的模式发布单个文件；其他模式发布含章节和时间索引的目录。
2. `/passthrough_seek/<source>.<mode>.seek.mp4` 在路径中保留 mode，避免播放器重发 Range 时丢失 query 后串模式。
3. `pipeline/passthrough_vmp4_frames.py` 构造普通 `ftyp + moov + mdat`，每帧一个 sample；预先固定 `stsz / co64 / stts / stss`，从而可将任意字节位置定位到帧和 GOP。
4. 真实视频按需 NVDEC → 处理 → NVENC，`iter_pynv_passthrough_annexb_frames()` 一次初始化后持续生成 HEVC access unit；帧 payload 按需缓存为 `runtime_cache/vmp4_frames/<digest>/frame_*.bin`。
5. 每帧固定字节预算，小于预算用合法 filler NAL 填充；原音频 sample 直接从源文件读取，并按 GOP 交错排列。HTTP 提供 HEAD、Range、206/416 与准确的布局长度。
6. seek 重定位时取消旧生成器、释放 Matter 池资源，再启动对应 GOP 的生成器；正常读取等待真实帧并用生成速度约束播放器读取速度。

### 扩展判断

- **Face Beauty 优先**：现有 `GpuFaceBeautyProcessor` 已逐帧处理并保持源尺寸，最接近 `make_frame_stage()` 的接口；需要封装 NV12/P016→RGB→美颜→NV12 与会话内 tracker 状态。
- **2D→3D 次之**：已有 DA3 + `GpuStereoRenderer`，但当前 live 实际是 flat SBS 3D，输出宽度为源的两倍。需统一输出尺寸、SBS 命名、预算、深度时序状态和 seek reset。不能把旧 `two_dvr` 整片 cache 构建代码视为已接通 slot_frames。
- **RM 需专门批处理适配**：`GpuRmProcessor.process_chunk()` 必须输入 8 帧，并有跨 chunk 反馈/检测缓存。应抽出连续处理帧迭代器，让 chunk 输出再逐帧进入公共编码器；同时明确 seek 起始上下文和结尾补帧。
- **SI 单独评估**：旧 `/media_si` progressive virtual MP4 仍在，但首次请求先构建整条混音 AAC sidecar，再读取 sample table 才能固定布局；当前 DLNA 用 `/si_live` 实时 MPEG-TS，不能直接复用“原音频原样复制”的视频 VMP4 音频路径。
- **字幕是额外差异**：live worker 有字幕烧录，当前 seek 帧生成器未调用字幕查找/叠加；外部字幕下载/声明不能等同于烧录支持。
- **光照匹配已有部分复用**：Green/Alpha 的底层处理含 light-match kernel，但 seek 帧缓存不含效果参数指纹，调参后需要明确失效与播放会话策略。

### 各功能接入细节与建议顺序

#### 1. Face Beauty：最适合先迁移

现有路径位于 `pipeline/pynv_stream.py::_worker_loop_face_beauty()`（3552 行起），真正处理器是 `offline/face_beauty_gpu.py::GpuFaceBeautyProcessor`。每个会话初始化一次，逐帧 `process(rgb_g)`，输出保持源尺寸；它已支持 2D 和 VR 人脸。`reset()` 可以重置 tracker。

建议将 NV12/P016→RGB、处理、RGB→NV12 和输出 ring 封装为 stage，通过现有 `make_frame_stage()` 同时供 live 和 seek 使用。复用现有启用及 PyNv 源门控；将运行时 preset、strength、检测/关键点间隔、最大人脸数等作为会话快照并加入缓存键。输出必须保持源尺寸，不能误走 `_vmp4_slot_output_size()` 默认的 `DECODE_MAX_SIDE` 缩放。

DLNA 当前在通用模式循环之前单独追加 Face Beauty 目录。因此只添加 seek 模式集合也不会自动替换这个目录，还需修改发布逻辑、object ID 反查、标题与 URL。

#### 2. 2D→3D：视频链路可复用，但几何和状态更复杂

现有路径位于 `pipeline/pynv_stream.py::_worker_loop_two_dvr()`（3172 行起）：DA3 深度推理→深度时序稳定→`GpuStereoRenderer`→SBS 输出。当前实时模式固定 `PROJECTION_FLAT_3D`，不是离线工具所有 VR 投影的总开关；名字 `two_dvr` 不应误导迁移范围。

输入宽度限制为 4096，SBS 输出宽度最大 8192。默认 MP4 外壳虽然已有 `two_dvr` 双宽分支，但 seek 生成器没有相应渲染分支，也不接受该 mode，因此它仍是实时目录功能。旧 `_vmp4_build_command()` 对 `two_dvr` 调离线工具，属于整片缓存构建方案。

需要统一真实 renderer 尺寸、MP4 template 尺寸和 DIDL resolution；按输出像素/实际编码成本设置预算，不能未经测量沿用单幅源画面的预算。seek 开始或切场需要 reset renderer、深度 EMA/光流和场景检测状态，持续编码时保留时序状态。支持双眼字幕和正确 SBS 命名。

#### 3. RM：适合连续帧迭代器，不能直接套同步逐帧 stage

现有路径位于 `pipeline/pynv_stream.py::_worker_loop_rm()`（3796 行起），调用 `pipeline/demosaic.py::GpuRmProcessor.process_chunk()`（835 行起），窗口 `WINDOW=8`。除 8 帧输入，处理器还有 `_cached_regions`、`_chunk_count`、`_region_states` 等跨 chunk 状态。支持 2D 和 SBS VR，VR 区域先重投影到平面再还原。

建议抽出连续处理帧迭代器：从 seek 所需 GOP 起点建立处理会话，先读 8 帧，批处理后按顺序产出 8 帧给公共 NVENC。最后不足 8 帧重复末帧补齐，但只写真实剩余帧。不要从逐帧 `process()` 返回模型中心帧来冒充整组输出，也不要为了每个 HTTP Range 重建模型。

当前 RM live 使用源帧率，而公共 seek layout 使用有效输出帧率（受全局 FPS cap 影响）。迁移前需确定继续用源帧率还是受 cap 控制，以及恢复模型看到连续源帧还是采样后的输出帧；布局、音视频时长和帧编号必须使用同一个规则。seek 后是否预读上下文是质量策略，尚未实测确定。

#### 4. SI：现成虚拟文件路径与当前实时路径是两种方案

当前 DLNA 的 `[SI]` 是单独目录，时间入口走 `/si_live/{name}?t=...`。旧 `/media_si` 在 `http_app/routes_media.py` 仍有 HEAD/GET/Range 支持；调用 `pipeline/si_virtual_mp4.py::build_progressive_si_virtual_mp4()`（2222 行起）。

旧方案先扫描源、生成整条混音 AAC sidecar，再用源视频 sample 和新音频 sample 构建虚拟 MP4，视频不转码。因此可作为较低开发量的恢复方案，但首播等待整条音频准备是它的代价。若要求真正随机位置即时混音，必须设计可提前固定大小的音频 sample 布局、分段边界的 AAC priming/延迟、混音参数快照和缓存，而不是把视频 VMP4 的源音频复制改成一个混音函数即可。

#### 5. SuperRes 放大目标：已经有实验路径，先测后开放

`utils/rtx_vsr.py::seek_supported_target()`（127 行起）默认只允许 Native，`PT_RTX_VSR_SEEK_ALLOW_UPSCALE=1` 可允许放大目标。代码已有放大输出尺寸和逐帧预算扩展，因此主要工作是性能、网络带宽、超预算率与播放器 seek 实测，然后调整默认能力门控。现有注释里的历史 FPS/带宽不能当成本次测试结果。

以上是按改造形态给出的建议顺序，不是工期估计。SI 可独立于视频迁移评估；字幕烧录应作为公共能力同时补齐。

### 重要风险

- 只添加 `SEEK_FRAME_MODES` 无法完成迁移：还有模式解析、启用门控、输出尺寸、模板、DLNA object ID、命名、缓存指纹和 UI 配置。
- 当前 `_seek_output_mode()` 仅接收四种模式，直接请求 `rm / face_beauty / two_dvr` 可能被回退为 Green/Alpha，不能据 URL 成功返回就认定功能支持。
- 固定预算并不保证编码永不超限：当前 filler 超限时会截断 payload，可能产生短暂损坏画面。新模式尤其 SBS/放大输出，需要真实素材测量。
- `_vmp4_frames_digest()` 包含源文件、mode、布局/预算等信息，但未包含完整效果参数。新增可调功能应带入处理参数快照，避免旧帧缓存串设置。
- 当前逐帧编码器要求 strong CFR 且依赖 PyNv GPU 路径；MP4 布局读取源 `moov`，MKV/VFR 不应假定能自动支持。

### 使用和边界

- 在美颜、RM、2D→3D、SI 设置内选择“虚拟 MP4”；此选择与原有 Green/Alpha/SuperRes/DLSS5 共用 `passthrough_playback_mode`。如从实时模式切换，按 UI 原有配置生效/服务重启方式应用设置。

- SI 接入已有 MP4 视频复制+整段混音 AAC 的虚拟文件实现；首次 HEAD/播放可能等待整段音频准备，Browse 不触发准备，提示已加入中英日翻译。没有实现 SI 分块实时 seek 混音。

## PC VR 播放器可行性研究：PTMediaServer + VRHeadTrackingPlayer + Godot OpenXR

### 请求、结论与验证范围

用户希望研究能否结合当前项目、VRHeadTrackingPlayer 和 Godot OpenXR，实现在软件内直接切换播放功能、无需 DLNA 的 PC VR 播放器。

**代码结构与官方文档支持这一方向。建议保留当前 Python GPU 处理后端，新增由主软件管理的 Godot XR 播放模块，复用 VRHeadTrackingPlayer 的格式识别、播放控制和投影经验。首版可使用仅本机 HTTP；高性能目标使用 GPU 纹理直连。** “无需 DLNA”可以先做到；“无需 HTTP、无需视频重编码”需要另做原生桥接。“软件内切换”可以作为统一操作体验实现，不要求 Python、WinForms 和 Godot 全部运行在同一进程。

本轮为调研，未实现播放器、未运行头显场景、未做 GPU 跨 API 互操作或音画同步实测。可行性和实施顺序是架构判断，不是已通过设备验收的承诺。没有改动业务代码、没有创建提交或 PR，也没有触发阶段性 summary。

### 1. 三个组件各自负责什么

| 组件 | 已有能力与可复用部分 | 仍需新增或适配 |
| --- | --- | --- |
| PTMediaServer | PySide6 UI、媒体库、PyNv/NVDEC、GPU 抠像、DA3 SBS、美颜、RM、VSR、字幕、光照匹配、SI、实时与虚拟 MP4 | 播放会话、播放页、处理结果的显示输出、会话内效果切换、GPU 图像桥接 |
| VRHeadTrackingPlayer | mpv 启动与 JSON IPC、文件/URL 打开、投影和双眼布局识别、模式记忆、mpv360 投影实现、桌面鼠标/摄像头控制 | 原生头显输出；当前是普通显示器观看 VR 视频的播放器，不能把嵌入的 mpv 窗口直接变成 OpenXR 双眼画面 |
| Godot OpenXR | 头显姿态、左右眼相机、控制器、XR 场景、桌面镜像、环境混合模式接口 | MP4/HEVC/AV1 播放后端、GPU 媒体纹理输入、各投影的着色器、效果控制 UI、音画同步 |

VRHeadTrackingPlayer 是 `.NET 8 / WinForms` 主窗口 + 外部 `mpv.exe --wid` 子窗口 + Windows named pipe JSON IPC，主要入口包括：

- `src/HeadTrackBridge/Host/PlayerWindow.cs`：文件、URL、播放菜单和窗口管理。
- `src/HeadTrackBridge/Mpv/MpvLauncher.cs`、`MpvIpcClient.cs`：进程、命令、属性观察、file-loaded 等事件。
- `src/HeadTrackBridge/Mpv/VideoFormat.cs`：分开表示 `Geometry`、`Stereo`、投影、识别可信度；包含 180/360、SBS/TB、鱼眼、柱面、EAC 等识别规则。
- `src/HeadTrackBridge/Mpv/PlayerModeController.cs`、`MpvCameraDriver.cs` 和 `mpv/shaders-src/mpv360-vr.glsl`：投影、FOV、眼睛选择与桌面视角控制。

适合复用的是格式规则、播放状态与投影数学，不是把 WinForms 主窗口搬进 PySide6 或 Godot。mpv360 的 `//!HOOK` 着色器语法和 Godot Shader 不兼容，需要移植。XR 输入应是未经过桌面视角裁剪的原始全景/SBS 帧，避免先 mpv360 投影再 Godot 投影。

真实头显姿态由 OpenXR 驱动 `XRCamera3D`，不应继续套用摄像头头部跟踪的增益和滤波；摄像头功能可作为桌面预览的可选能力。Godot Shader 的 `VIEW_INDEX` 可区分左右眼，为 SBS/TB 选择各自采样区域。2:1 图像仍有 mono 360 与 SBS VR180 的歧义，需要显式元数据、手动修正及每文件记忆。

### 2. 当前项目已经有可绕开 DLNA 的接入点

DLNA/SSDP 是发现和目录层，当前实际媒体输出已经是 HTTP：

- `/media/{name}`：原始媒体、HEAD 与 Range。
- `/passthrough_seek/{name}`：逐帧虚拟 MP4，模式通常保留在 `.<mode>.seek.mp4` 路径中。
- `/passthrough_live/{name}?mode=...&t=...`：处理后的实时流，可按源时间起播。
- `/media_si/{name}` 与 `/si_live/{name}`：现有 SI 混音输出。

因此内置播放模块可以直接打开本机路径或 `127.0.0.1` 媒体 URL，不需要 SSDP、UPnP Browse 或外部 DLNA 播放器。

不过“只改 URL”还不能完成产品：`main.py` 在启动 HTTP 前会调用防火墙规则逻辑并无条件启动 `SSDPServer`，HTTP 绑定 `0.0.0.0`；`http_app/server.py::create_app()` 也同时注册了控制、DLNA 和媒体路由。需要提取播放器专用启动入口，共用必要的媒体库/模型初始化，按模式选择监听器，只绑定 loopback，并跳过 DLNA 发现及其启动副作用。`create_app()` 本身不会启动 SSDP，但它并不等同于完整的播放器后端初始化。

当前 `pipeline/pynv_stream.py::SEEK_FRAME_MODES` 已包含 `green / alpha / superres / dlss5 / two_dvr / face_beauty / rm`。`make_frame_stage()` 以及 `pipeline/seek_effects.py` 的逐帧/批处理适配器是后续抽取处理输出的良好边界。

`iter_pynv_passthrough_annexb_frames()` 当前输出的是 HEVC access unit；可以在 `GpuNv12AppFrame(out_nv12, ...)` 进入 `enc.Encode()` 之前抽出显示用 FrameSink，但不能把“已有迭代器”当成“已经有显示纹理接口”。Green/Alpha 的 Matter、AlphaPacker、GPU 输出 ring、字幕顺序、资源释放和各 stage 的状态也需随之整理。

### 3. 建议架构与两条接入路线

产品入口建议是当前软件新增“播放”页：选本地文件 → 选择桌面/头显输出 → 选择效果 → 播放、拖动、调参。PC VR 输出由主软件自动管理 Godot 辅助进程；效果控制也可在头显面板中出现，二者控制同一 PlaybackSession。

统一会话至少保存：源文件/媒体 ID、源时间、暂停与音量、音轨、字幕、投影、双目布局/左右交换、显示尺寸/方向、效果参数快照、参数版本和处理 generation。进程间使用本机控制 IPC，传命令和状态，不传 JSON 视频像素。

#### 路线 A：先验证产品体验

```text
本地文件 → 当前 GPU 处理 → NVENC/虚拟 MP4 或实时流
                              ↓ 127.0.0.1 HTTP
                      libmpv/FFmpeg 视频后端
                              ↓ 视频纹理
                  Godot 投影/双眼渲染 → OpenXR → 头显
```

- 原片可以由播放后端直接读本地路径；处理模式先复用现有 HTTP 输出。
- 无 DLNA，但仍有处理视频的编码、解码和纹理传递开销。
- 虚拟 MP4 首版可继续沿用现有源格式、CFR、模式启用与 GPU 门控；不能据此宣称任意 MKV/VFR 都已支持。
- 第一版先支持“一个主要视频处理模式 + 字幕/基础调节”，不要把独立 URL 模式理解为任意效果可以同时叠加。
- 使用现有 SI MP4 路线，首次可能等待整片混音 AAC 构建；无缝 SI 切换需另做音频会话/实时混音。

Godot 原生 `VideoStreamPlayer` 核心仅支持 Ogg Theora，Theora 为 CPU 解码，并且内置实现不支持 URL 视频流。因此不能用它直接承接当前 HEVC/MP4 或 HTTP 链路，需要原生扩展或自有播放器后端。

本轮检查了社区候选 `VersaYT/godot_mpv`：其 README 标注 Godot 4.4，支持本地和 HTTP；源码实际使用 libmpv OpenGL FBO、`glReadPixels`、`memcpy`、`Image::set_data`，随后创建新 `ImageTexture`。它可以作为低分辨率原型参考，不能据仓库介绍认定它已具备适合本项目的 8K、低拷贝、4.7.2 OpenXR 播放能力。其 `hwdec=auto-safe` 也需实际检查选中的 decoder，不能等同于零拷贝。

相关源码取证副本保留在被 Git 忽略的 `debug_output/pcvr_research/godot_mpv_player.cpp`、`.h`。未编译或运行该插件。

若保留 8192×4096 RGBA8 帧，一帧为 128 MiB，60fps 单方向数据量为 7.5 GiB/s；下载再上传就是 15 GiB/s 的两方向像素流量，尚不含额外 CPU memcpy 和同步。此值是按尺寸推算的数据量，不是本机实测带宽，也不说明插件默认输出就是 8K。

#### 路线 B：面向高性能的 GPU 直连

```text
本地文件 → NVDEC → CUDA/ONNX/NGX 视频效果
                           ↓ GPU NV12/颜色纹理 + 可选 Alpha + PTS
               C++ 原生桥接 / Windows 共享 GPU 资源
                           ↓ Godot 可用的 Vulkan 纹理
                  Godot 投影/双眼渲染 → OpenXR → 头显
```

- 软件自身的处理显示链路绕过 NVENC、虚拟 MP4 和播放器二次解码；控制层可以继续使用本机 IPC。
- 这是需要新增的重要工程模块，不能只把 CuPy 指针交给 Godot。
- 候选是 Vulkan external memory + Win32 handle、CUDA external memory/semaphore、Godot GDExtension + `RenderingDevice` / `Texture2DRD`。
- Godot 文档有 `texture_create_from_extension()` 包装已有 `VkImage` 的接口；这不自动解决可共享资源的创建、同一物理 GPU/逻辑设备、图像布局、跨进程句柄传递、队列/信号量同步或渲染线程调度。
- 必须用小探针确认当前 Godot 版本的设备扩展和渲染接口是否足以完成可靠导入及同步；若不足，可能需要更深的原生模块或引擎适配。此处尚未证明可完全靠现成 GDExtension 达成。
- libmpv 的公共 Render API 当前列出的后端为 OpenGL 与软件输出，并不是直接提供 Godot Vulkan Texture。mpv 主播放器支持 Vulkan，也不能据此推导 libmpv 公共 Render API 可以直接交出 Vulkan 帧。
- Python 各 stage 常用 NV12；显示桥需要处理 pitch、生命周期、NV12/P016 的颜色转换、范围和色域。避免整帧 CPU 往返；必要的 GPU 内复制仍需计入性能预算，不承诺端到端严格零拷贝。
- 音频必须另行解码/播放或混音，明确一个主时钟，用视频 PTS 同步。需要音频输出设备切换、seek flush、暂停恢复、字幕时间线、10-bit/HDR/SDR 策略和背压。

### 4. 软件内切换怎样实现

当前 `ui/pages/dashboard_page.py::set_server_running()` 会锁住大多数首页功能开关，只放行 light；现有运行时控制 API 主要覆盖 light、SI、美颜、RM 等调参。不能把这些现有开关解除锁定就当成播放器实时切换。

新播放会话应区分两类动作：

1. **显示参数变化**：投影、左右眼交换、屏幕距离/尺寸、亮度、着色器背景/透明度、独立字幕等，可以在已有纹理上切换，不重建媒体时间线。
2. **处理链变化**：原片 ↔ DA3 ↔ VSR ↔ RM ↔ 美颜等，保存当前源时间、暂停、音轨与字幕状态，取消旧 generation，预热选中的 stage，在对应源时间开始新的输出，等首帧可用再交接。首版可以短暂停顿/缓冲；“点击可切换”不等于已经实现无黑屏、无音频间断的瞬时切换。

路线 A 的核心动作是保存时间、换媒体 URL、等待 file-loaded、seek/确认新时间并恢复状态，不能简单依赖 `loadfile` 保留进度。live 流的 `t` 是源起播偏移，还需正确处理其播放器相对时间与源绝对时间。所有重载要同时更新投影、输出尺寸和缓存参数版本。

路线 B 可保留解码/音频会话，更换处理 stage；若输出尺寸发生变化（如 2D→3D 输出宽度加倍），必须重建相应纹理/ring 和采样参数。RVM、DA3、RM、美颜 tracker 等有状态，seek 或切换需要各自的 reset/上下文预热；RM 仍需 8 帧批处理。不要一次预热所有模型占满 16GB 显存。

如果用户要求“美颜 + 抠像 + 超分”等同时开启，需要进一步设计效果链：处理顺序、颜色/Alpha 布局、左右眼协调、输出尺寸、状态重置、预算与兼容矩阵。现有模式分支不能自动满足这种组合。

### 5. Alpha / 绿幕与真实 MR 的独立限制

当前 `pipeline/alpha_packer.py` 是面向外部播放器的特殊视频协议：SBS half-equirectangular 180 先投影到 fisheye SBS，再把 mask 写进六块布局；它不是带原生 RGBA 通道的普通 HEVC。Godot 显示该输出需专门解包，不能当普通 SBS 播。

- 路线 A：可以先支持普通/绿幕显示，再增加与现有 AlphaPacker 一致的六块解包 Shader、对应鱼眼采样及双眼验证。
- 路线 B：建议在打包前直接输出颜色 + Alpha mask，不再使用外部播放器专用的六块视频编码；需要明确 mask 的分辨率、投影、左右眼和采样边界。
- “视频背景透明”可以先叠在虚拟影院/自选背景上，不依赖头显摄像头。
- “透明位置看到真实房间”额外依赖运行时提供环境 alpha blend / passthrough 扩展，以及相应 Godot vendor 插件与透明 XR viewport。

Godot 官方说明各平台 passthrough 实现不同，需要查询支持的 environment blend modes；Meta Quest 等还需要 OpenXR Vendors 插件。不能因为 OpenXR 普通 VR 成功，就认定 SteamVR、VDXR 或其他 PC Runtime 都能做相同 MR。

Meta 官方当前把 Passthrough over Link 描述为开发者预览功能，并要求开发者账号、Developer Runtime Features、Passthrough over Meta Quest Link 等条件。因此 Quest PC VR 中“抠像主体叠真实环境”应作为独立验证任务；不能把这条开发预览路径直接承诺为面向所有用户的通用 MR 方案。

PC VR 依然需要头显连接与 Runtime。Quest 通过 Link/Air Link 等 PC VR 连接观看时，媒体由 PC 应用读取并渲染，头显接收 PC VR 画面；这条连接不是 DLNA。如果用无线/串流连接，运行时仍可能编码最终头显画面，路线 B 绕过的是本软件内部多余的处理视频编码，不能保证整个 PC→头显链路没有编码。

普通 VR180/360 视频只有记录下来的视点；接入支持 6DoF 姿态的 OpenXR 不会自动生成自由移动后的真实视差。首版应正确实现全景观看旋转/重置，2D→3D 按平面/曲面双目屏幕呈现；当前 DA3 SBS 不是可自由走动的 6DoF 重建场景。

### 6. 建议落地顺序与验收门槛

建议先锁定本机已有 Godot 4.7.2 及匹配的扩展/导出模板版本，以 Windows x64、当前 SteamVR 配置和实际可连接头显作为首轮测试组合。Godot 官方目前建议 desktop XR 用 Mobile renderer；优先试 Vulkan/Mobile。Vulkan OpenXR 需要在进程启动时启用，可由主软件在进入头显模式时管理 `--xr-mode on` 的 XR 进程，不把改变效果当成重新初始化 Runtime。

1. **最小 XR 验证**：静态左右眼测试图、正确 SBS/TB/180/360 采样、头部旋转、reset、控制器操作、未连接设备时的状态与桌面回退。
2. **本地播放验证**：先 1080p/4K 原片与一个处理模式，验证音频、暂停、拖动、首帧、输出尺寸、桌面/头显切换和软件统一关闭。
3. **同进度效果切换**：原片、美颜、2D→3D 等按同一源时间切换，验证音轨/字幕/暂停状态不丢失，取消旧任务、缓存不串设置；记录实际切换延迟而不预设“零停顿”。
4. **性能探针**：测解码、模型、上传/互操作、XR GPU frame time、视频有效 FPS、掉帧、音画偏差、显存；至少一次连续 30 分钟播放及重复 seek/切换。头显 72/90Hz 渲染与视频 24/30/60fps 是两个频率，视频低帧率不应阻塞头部视角更新。90Hz XR 的每帧预算约 11.1ms。
5. **GPU 桥验证**：先传一张已知图再传连续带 PTS 的处理帧，检查同步、色彩、资源回收；再扩大到 4K/8K。已有 VSR 高负载表现不能推导全部效果都可实时叠加，需要按分辨率/模型提供可测的降级选项。
6. **MR 独立验证**：查询实际 Runtime 扩展/混合模式，测试普通透明合成、Alpha 六块解包或直接 mask、真实环境透视；不支持时明确提供虚拟背景模式。

首轮值得实现的垂直原型是：**本地文件 → 一种现有视频效果 → Godot 双眼输出 → 主软件同进度切换原片/效果**。通过后再决定 libmpv 桥的改造程度与 GPU 直连投入；先列出所有功能按钮不足以证明播放器方案成立。

## 有道 R2T2 / T3PO 实时听译字幕可行性调研

调研日期：2026-10-02（Asia/Shanghai）。用户要求“先研究，不改代码”。本节基于 `codex/virtual-mp4-modes` 分支、HEAD `d6e0af3` 及当前未提交的虚拟 MP4/公共字幕实现；仅追加交接文档，没有实施接入、安装依赖、下载模型或运行模型推理。上面的测试数字属于此前虚拟 MP4 工作，不是本次听译性能验证。

### 判断

**可以接入，但需要音频听译任务、动态字幕时间轴和编码前就绪控制，不能只把模型调用塞进现有字幕渲染函数。** 中英方向适合作为首个验证范围；日语→中文应先独立验证。建议先把推理部署成独立服务，利用本地视频可以提前读取音轨的条件，在视频编码前准备对应字幕，再复用现有 GPU 烧录和 VR 双眼/投影能力。

本机 RTX 5060 Ti 16GB 同时承担视频效果时，全套模型的显存和吞吐是主要限制；不能根据官方 ASR 延迟直接承诺项目端到端实时性能。

### 可复用的官方接口

- R2T2 提供 WebSocket `/asr_stream_api_v1`。当前源码要求先发送含 requestId、语言等字段的 JSON 握手，再发送 16kHz 单声道 PCM16LE，结束时发送 EOS 标记。响应包含增量 text、reset 和处理耗时；**当前协议没有直接提供可用于 SRT 的源音频起止时间**。reset 用于结束/重置 ASR 段，要触发译文尾部 flush，并处理异常与重连，不能理解成随意清空所有字幕。[官方 ASR 客户端适配](https://github.com/netease-youdao/Confucius4-T3PO/blob/main/inference/asr.py)。
- T3PO 已提供 `StreamingTextTranslator.feed()/flush()`，以及单独 ASR 服务与翻译服务的串联示例，可借鉴其会话状态。翻译返回 source/text 等事件，仍需项目补充媒体时间映射。[官方仓库](https://github.com/netease-youdao/Confucius4-T3PO)、[事件实现](https://github.com/netease-youdao/Confucius4-T3PO/blob/main/inference/translation.py)。
- T3PO GGUF 可通过 llama.cpp 的兼容 HTTP 接口加载；即使复用标准接口，也必须保留 WAIT/TRANS 与历史协议，不能把每个 ASR 碎片当独立整句翻译。[官方 GGUF 使用说明](https://huggingface.co/netease-youdao/Confucius4-T3PO-GGUF)。

源码额外发现：R2T2 的示例 WebSocket 服务将 `gpu_memory_utilization` 写为 0.95，不能照搬到与视频处理共用的显卡上；需要单独评估资源配置。这是示例服务设置，不是模型实际必须占用 95% 显存。[当前服务源码](https://github.com/netease-youdao/Confucius4-R2T2/blob/master/ws_server.py)。

### 建议的处理链和时间规则

```text
源视频选定音轨
  → FFmpeg/PyAV 提取 16kHz mono PCM（保留媒体时间关系）
  → R2T2 稳定原文增量
  → T3PO 有状态翻译 / VAD 段尾 flush
  → SubtitleCue 时间轴与持久缓存
  → 现有文字渲染 / GPU 双眼及 Alpha 叠加
  → NVENC → live 或虚拟 MP4
```

关键是项目传输的实时流来自本地文件，允许先读取未来音频。先准备一段字幕，再维持编码位置前方的听译窗口；窗口和首播等待时长由实际测量确定。编码所需字幕还未确定时，要等待或给出明确失败策略。若把空字幕帧先写入缓存，后来的译文无法出现在已经发送/缓存的画面中。

时间轴应以源视频/音轨 PTS 为准，建立解码段起点与 PCM 累计样本数的关系，并处理音轨 start_time、seek 解码实际位置和重采样。接收字幕的墙钟时间及请求处理耗时都不能直接当作说话发生时间。初版可按 VAD/短段给粗粒度边界；精确逐词同步需要额外对齐验证。译文事件消耗的原文范围也必须映射到这些边界。

真正来自麦克风或直播的输入无法提前读取：若仍采用硬字幕，必须同时延后音频和视频，让译文赶上编码。只延迟视频会造成音画不同步。官方 200～600ms 是 ASR 宣称值，整条链还包含语义等待、翻译计算、排队、渲染、编码和播放器缓冲，当前没有本机端到端数字。

### 虚拟 MP4 / seek 的特别要求

1. **先字幕后帧缓存。** 当前帧写入 `frame_XXXXXX.bin` 后通常直接复用；已有字幕文件指纹只能处理静态文件变化。新听译应使用稳定任务身份与封定片段/会话版本，避免随着每次字幕追加改变整片布局身份，也避免复用旧无字帧。
2. **同一虚拟文件版本保持内容一致。** 同一个 URL、缓存身份和 Range 布局下的已公开帧不应随后被另一版译文覆盖。修改模型、语向或字幕内容需形成新的结果/播放版本。
3. **拖动重定位。** 未缓存位置从附近重新提取音频，准备少量前文后再生成目标 GOP；重置 ASR/T3PO 当前状态，或恢复对应字幕缓存。上下文量需要验证，不能沿用前一个时间位置的未翻译缓冲。
4. **取消与共享。** 用 generation/cancel 状态丢弃旧任务响应；同一视频音轨、语向和模型版本可共享已封定字幕，各播放会话仍独立维护请求位置。DLNA Range 可能是探测/预取，不能当作准确的客户端播放时钟。
5. **缓存键至少包含** 源文件身份、音轨、语向、ASR/翻译模型与量化版本、分段/时间策略、术语设置；视觉帧另外包含样式/投影与视觉效果快照。用户原有手工字幕应保留，生成字幕先存 runtime_cache，由显式选择确定使用哪条轨道。

部署建议：

- **先验证独立 Linux/WSL2 推理服务。** Windows 主程序以 WebSocket/HTTP 客户端接入；使用独立环境隔离项目现有 CuPy/ORT/CUDA 依赖。WSL2 仍共享本机显卡，不会增加显存；分机器或第二张卡才真正隔离 GPU 资源。
- **原生 Windows 全本地作为后续专项。** vLLM 官方不支持原生 Windows；R2T2 官方 `r2t2_llama` 预编译产物是 Linux x86_64/CUDA/CPython3.12 的 `.so`，不是 Windows DLL。其全 llama 音频编码与推荐混合路径还有质量差别，不能看到 GGUF 就认定 Windows 流式能力可直接使用。[vLLM 平台要求](https://docs.vllm.ai/en/stable/getting_started/installation/gpu/)、[R2T2 llama 后端说明](https://github.com/netease-youdao/Confucius4-R2T2/blob/master/r2t2_llama/README.md)。
- 若最终必须单卡 16GB 同时跑重视频效果，可评估提前整段/整片生成字幕后卸载模型，或切换更小的翻译后端；这需要产品在首播等待、持续听译和画面效果之间作选择，当前不预设性能结论。
