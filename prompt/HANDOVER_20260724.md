# Work Handover (2026-07-24)

## Request

New feature "VR转平面后解码" (VR-to-flat before restoration): for VR180 sources,
gnomonic-project each detected mosaic region from the equirect eye to a flat
(rectilinear) view, restore it there, then reproject + alpha-composite back.
Ship it as a config switch (default on, UI later). The open question was how to
derive yaw/pitch automatically from a detected mosaic region.

Reference implementation studied: `VR_Video_Toolbox/area_selection_vr2flat`
(`logic.py` pipeline + `main.py` click-to-select mapping).

## Key Findings

**Auto yaw/pitch is analytic, not a search.** hequirect spans 180x180 deg with a
linear pixel<->angle mapping, so a detected box maps straight to a view (same
formula the reference GUI uses for click-selection), in eye-local coords:

    yaw   = (ecx/eye_w)*180 - 90
    pitch = 90 - (ecy/eye_h)*180
    d_fov = max(bw/eye_w, bh/eye_h)*180 * margin

**Rotation order matters and is now locked.** Forward (equirect->flat) uses
`rorder=ypr` with +yaw/+pitch; the inverse overlay uses `rorder=rpy` with
negated angles + `alpha_mask=1`. Rotations do not commute, so the inverse needs
reversed order *and* reversed angles to cancel exactly.

**Why quality improves:** on equirect the mosaic block is skewed/stretched by the
projection; on the flat view it becomes an axis-aligned square, which is what the
restorer handles best.

## Done

### Stage 1 - offline prototype (quality validation)

`tools/rm_vr2flat_prototype.py`: reuses ffmpeg `v360` (identical math to the
reference tool) but swaps in this project's RM engine and derives the view from
the detector instead of manual selection. Single eye, one representative view
for the clip. Produced a baseline-vs-new comparison confirming the hypothesis:
clearly sharper texture, correct alignment on reprojection.

### Stage 2 - GPU integration (the shipping path)

ffmpeg `v360` filter params cannot vary per frame, so per-frame/per-region views
require our own GPU reprojection.

1. New `pipeline/vr_reproject.py`: CuPy RawKernels `equirect_to_flat_u8`
   (forward) and `flat_to_equirect_u8` (inverse, emits patch + alpha), bilinear.
   Host builds the rotation once; forward uses R, inverse uses R^T, so they are
   exact inverses. `fov_to_range()` mirrors v360's `fov_from_dfov`.
   **Convention locked to v360: R = Ry(yaw) @ Rx(-pitch) @ Rz(roll)** -- note the
   negated pitch; v360's pitch sign is opposite a naive right-handed Rx.
2. `pipeline/demosaic.py`: `GpuRmProcessor.process_chunk` gained a `vr` branch
   (SBS detected via `W >= 2*H`). Helpers `_region_view()` (box -> eye + angles)
   and `_eye_crop()` (composite window = box grown 45%). Fill loop projects each
   region to a 256x256 flat for the restorer; composite loop reprojects the
   restored flat and alpha-blends it back. Per-frame, per-region, per-eye.
3. `config.py`: `RM_VR2FLAT_DECODE` (default on, `PT_RM_VR2FLAT_DECODE`) and
   `RM_VR2FLAT_FOV_MARGIN` (1.4).

Offline and realtime [RM] share `GpuRmProcessor`, so both get this.

## Verification

- Forward reprojection vs ffmpeg v360, same frame/params: **PSNR 48.29 dB**
  (convention scan over sign/order variants; next-best variant only ~16 dB).
- Forward->inverse round-trip in the covered region: **PSNR 47.41 dB**, max
  channel diff 26; coverage bbox correctly encloses the detected box with the
  expected fov margin.
- End-to-end offline on a 4096x2048 VR180 SBS sample, 480 frames, switch off vs
  on: both complete; **both eyes restored**; no misalignment or seams; the
  vr2flat output is visibly sharper than the direct-equirect baseline.
- Performance: **39.4 fps (on) vs 45.6 fps (off)**, ~14% cost -- the flat view is
  only 256x256 and the inverse pass runs on a small crop.

### Stage 3 - optimizations (same day)

1. **Zero-copy forward.** The forward kernel took a contiguous eye, so
   `to_flat()` copied the 2048x2048 eye per region per frame (repeatedly, when a
   frame had several regions). It now takes `src_stride_w` + `eye_origin` and
   addresses the eye in place inside the full SBS frame; `out=` writes straight
   into the restorer batch slot, removing another copy.
2. **Fused composite.** The inverse path allocated a patch + alpha and then did
   the blend in Python (four float32 temporaries per region per frame). New
   kernel `flat_to_equirect_blend_u8` reprojects and alpha-blends directly into
   the destination frame, allocating nothing per call. The patch+alpha kernel is
   kept for validation.
3. **Edge feathering.** Alpha was a hard 0/255 edge; it now fades toward the flat
   view's border via `RM_VR2FLAT_EDGE_FEATHER` (default 0.12), removing any hard
   seam. Shared device helpers (`project_to_flat`/`sample_flat`/`edge_alpha`)
   back both inverse kernels.

Contiguity is enforced where it matters: inputs get a no-op `ascontiguousarray`,
while `blend_into` raises on a non-contiguous destination rather than silently
copying (which would discard the composite).

### Stage 3 verification

- Forward vs ffmpeg is **unchanged at 48.29 dB** for all three addressing modes:
  single-eye, zero-copy from a SBS frame's right-eye offset, and `out=` into a
  batch slot -- the zero-copy rework introduces no error.
- Round-trip unchanged at 47.41 dB.
- `blend_into` vs the manual patch/alpha composite: **99 dB (identical)** at
  feather=0; at feather=0.12 the alpha goes from 2 to 256 levels as intended.
- End-to-end: **42.6 fps**, up from 39.4 fps; overhead vs the switch-off baseline
  (45.6 fps) drops from ~14% to **~6.6%**.
- Output vs the pre-optimization run: mean |diff| 0.12 (max 57, only in the
  feather band) -- numerically equivalent, with a softer edge.

### Stage 4 - roll convention (bug found and fixed)

Roll was previously unvalidated because it is always 0 in the current pipeline.
Probing it against v360 required non-zero yaw *and* pitch *and* roll at once --
with yaw=pitch=0 the ordering of Rz is unobservable.

Scanning roll sign x Rz position found **`Rz(-roll)` with Rz rightmost**, chosen
independently and unambiguously at roll=+25 (50.04 dB) and roll=-40 (47.39 dB);
every other variant scored ~15 dB. **The shipped code had `Rz(+roll)`** and
scored only 15.38 / 14.03 dB -- a latent sign bug, harmless so far only because
roll=0 makes Rz the identity, but wrong the moment roll is used.

Fixed: `R = Ry(yaw) @ Rx(-pitch) @ Rz(-roll)`. Both pitch and roll are negated
relative to the naive right-handed axes.

Verified after the fix: roll=0 unchanged at 48.29 dB and the whole roll=0
regression set (A-E above) unchanged; roll=+25 -> 50.04 dB, roll=-40 -> 47.39 dB;
round-trip stays 47.4-48.7 dB at roll = 0 / +25 / -40 / +90 with identical
coverage, and `blend_into` matches the manual composite at 99 dB for every roll.
