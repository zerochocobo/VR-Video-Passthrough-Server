# HANDOVER 2026-07-26

## Design note: one-click GPU cache repair for existing users

The proposed repair button is appropriate, but it must not delete the whole
`runtime_cache` tree. That root currently also contains user/application state
and non-GPU data, including `ui_settings.json`, `ui_settings_meta.json`,
`library_index.sqlite*`, thumbnails, audio/virtual-media caches, and packaged or
downloaded resources such as `clip_text_onnx`.

### Recommended UX

1. Primary entry: when the startup overlay reaches `failed` before the server
   listens, show **Repair GPU cache and restart** beside Copy Report.
2. Secondary entry: Settings or Tools -> Troubleshooting ->
   **Reset GPU acceleration cache** so users can run it proactively.
3. Confirmation text should explain that settings and media files are kept,
   the next startup may take 1-3 minutes, and TensorRT acceleration may need to
   be rebuilt afterward.
4. Disable repair while server/offline GPU processes are running; stop them
   first or ask the user to stop them.
5. Prefer atomic rename/quarantine of selected paths, then restart. Delete the
   active quarantine after a successful startup; prune abandoned quarantines
   after a bounded retention window on a later application launch.
   This avoids half-deleted caches and handles recovery better than deleting
   files in place.

### Suggested repair scope

Delete/quarantine generated GPU artifacts:

- `runtime_cache/cuda_compute_cache`
- `runtime_cache/cupy`
- `runtime_cache/ort`
- `runtime_cache/tmp`
- `runtime_cache/gpu_warmup_marker.json`
- `runtime_cache/.warmup.lock`
- `runtime_cache/trt_engines`
- `runtime_cache/da3_trt`
- `runtime_cache/demosaic_trt`
- `runtime_cache/nvds_trt`
- `runtime_cache/vsr_onnx_trt`

Do not delete:

- `runtime_cache/ui_settings.json`
- `runtime_cache/ui_settings_meta.json`
- `runtime_cache/library_index.sqlite*`
- `runtime_cache/clip_text_onnx`
- thumbnails, request history, logs, media files, model source files
- unrelated audio and virtual-media caches unless a separate storage-cleanup
  command explicitly covers them

The code should use an allowlist of known GPU-cache targets rather than a
denylist or recursive deletion of the root.

### Repair startup flow

1. Record the original failure report and child exit code.
2. Quarantine the allowlisted GPU cache paths.
3. Restart once in safe CUDA mode (`CUDAExecutionProvider,CPUExecutionProvider`)
   without TRT. Do not loop automatically.
4. If startup succeeds, tell the user the repair succeeded and TensorRT caches
   can be rebuilt later from their existing configuration dialogs.
5. If it still fails, keep the new diagnostic report and direct the user to
   Copy Report; the issue is likely driver/runtime compatibility rather than
   cache corruption.

### Useful distinction

A smaller **Clear TensorRT cache** command already exists in
`TensorRTConfigDialog`; it is not sufficient for this incident because the
suspected failure can be in CUDA/CuPy/ORT warmup. The new command should be
named GPU acceleration cache repair/reset so users do not confuse the two.

No production code was changed in this design discussion.

## Implementation completed

The design above has now been implemented (the final sentence above describes
the earlier design-only checkpoint).

### User-facing behavior

- Startup failure overlay offers **Repair GPU cache and restart** for failures
  outside known non-GPU stages such as firewall/SSDP/HTTP binding.
- Settings now contains **Troubleshooting -> Reset GPU acceleration cache**.
- Confirmation clearly states that videos, models, media library, and settings
  are preserved; first startup can take 1-3 minutes; TRT must be rebuilt.
- Repair quarantines only the allowlisted generated GPU paths. It never removes
  the `runtime_cache` root.
- If realtime TensorRT was enabled before repair, the restart sets the one-shot
  `PT_GPU_REPAIR_REBUILD_TRT=1` flag. The server rebuilds realtime RVM TRT in an
  isolated child process before provider validation, then enables the new TRT
  cache in the same startup. A native TRT build crash cannot terminate the
  server parent; a failed build falls back to CUDA and startup continues.
- Optional DA3/RM TensorRT warmups run normally and can recreate their cleared
  caches. After successful listening, the quarantine is deleted and the user
  receives a provider-specific success message. On failure, it remains
  available for diagnosis.

### GPU-free desktop startup

- `ui.settings.Settings.server_env()` no longer validates TRT in the UI. It
  forwards the user's requested provider chain; `main._validate_tensorrt_provider`
  performs the authoritative fingerprint validation and CUDA fallback in the
  child server.
- Settings/offline pages use `cache_artifact_status()`, which checks only
  manifest/file structure and never probes NVML/CUDA/ORT/TRT.
- Automatic GPU concurrency detection was removed from `config.py` import time.
  Config defaults to 1 for an unresolved `auto`; the server child resolves VRAM
  after startup before the matter pool and HTTP routes are created.
- The UI-side unsupported-GPU `nvidia-smi` check was removed; the existing
  server-side requirement check remains authoritative.
- Verified by constructing `MainWindow` while both `subprocess.run` and
  `subprocess.check_output` raise: `UI_SUBPROCESS_PROBE_FREE_OK`.

### Diagnostics

- `ServerProcess` now preserves and logs the real child exit code.
- The synthesized warmup-exit detail includes signed and hexadecimal forms,
  allowing Windows NTSTATUS crashes such as `0xC0000005` to be identified.

### Verification

- Focused changed-area suite: 58 passed, 20 subtests passed.
- Project suite excluding the known pre-existing translation-key parity test:
  511 passed, 2 skipped, 59 subtests passed.
- The remaining full-suite failure is an existing `ja_JP` translation mismatch

## Full startup progress redesign

The previous overlay treated GPU warmup as the whole startup. Independent
components wrote unrelated 0–100% values, while media indexing, auxiliary TRT
models, runtime-pool setup, and network startup were either missing or squeezed
into the final few percent. Its ETA represented a local blocking call but the UI
subtracted total elapsed time from it, so estimates became increasingly wrong as
the startup path grew.

### New startup plan

- `main._startup_plan_steps()` builds an ordered plan from the actual active
  configuration. Conditional steps cover:
  - All Videos media indexing;
  - GPU compatibility;
  - repair-time realtime TRT rebuilding and normal TRT validation;
  - RTX VSR preflight;
  - RVM runtime/session/TRT/inference/composite initialization;
  - DA3 and mosaic-restoration TRT warmup;
  - NVENC preflight;
  - media runtime pool, firewall, SSDP, HTTP application creation, and listen.
- `utils.startup_status.configure_startup_plan()` maps each component's local
  progress into a single monotonic weighted global progress value. Existing
  warmup producers remain compatible and no longer need to agree on global
  percentages.
- Heartbeats now advance only the active plan segment and report whole-startup
  remaining time. The status payload includes `plan_active`, `plan_steps`,
  `plan_estimate_sec`, `total_elapsed_sec`, and `step_elapsed_sec`.
- Successful starts save per-step EWMA timings to
  `runtime_cache/startup_step_timings.json`. Later starts load these timings
  with `utf-8-sig`, so weights and ETA adapt to the current machine, enabled
  features, model caches, and media-library size.

### Overlay changes

- Added friendly zh_CN/en_US/ja_JP labels for process startup, All Videos
  indexing, GPU compatibility, TRT validation, RTX VSR preflight, and runtime
  pool setup.
- Plan-backed startup always uses a determinate bar; the legacy marquee remains
  only as fallback for servers/status payloads without the new plan.
- Step numbering now represents the complete configured startup path rather
  than only GPU warmup.
- `eta_sec` is displayed directly as total remaining startup time, alongside
  total elapsed time, matching the status protocol's documented semantics.

### Verification

- Added tests for weighted local-to-global progress mapping, remaining ETA,
  timing-history persistence, conditional plan construction, and planned UI
  display.
- Focused affected suite: `98 passed, 27 subtests passed`.
- Project suite excluding the pre-existing ja_JP parity failure:
  `519 passed, 2 skipped, 62 subtests passed`.
- Translation JSON validation with `utf-8-sig` and `git diff --check` pass.

## Startup plan review fixes

The first plan implementation had two real-world convergence defects: runtime-
skipped steps retained their default weights forever, and heartbeat callers used
hard-coded durations even after the plan had learned different per-machine
estimates.

### Skipped steps and provider validation

- Startup status now tracks `_plan_seen`. On a successful `listening` state,
  every configured step that was never published is learned as a near-zero
  duration. Runtime-skipped static TRT, DA3, and RM steps therefore collapse to
  0.1 seconds (the load-time floor) on the following start instead of permanently
  reserving 12/45/60 seconds.
- `reconfigure_startup_plan()` updates the remaining plan after TensorRT cache
  validation without resetting elapsed time, seen steps, or monotonic progress.
  Steps removed by reconfiguration are also recorded as skipped immediately.
- Pre-validation planning now uses the conservative CUDA inference budget. A
  successful TRT validation shortens the plan; stale-cache CUDA fallback cannot
  expand a 12-second plan into a 90-second plan and leave the bar waiting to
  catch up.
- ORT inference timing history is provider-profiled (`@trt`, `@cuda`, `@cpu`,
  plus the pre-validation `@pending` profile). Fast TRT history can no longer
  under-budget CUDA fallback after a driver/cache change.

### Heartbeat and overlay compatibility

- In plan mode, `start_heartbeat()` uses the active plan step's learned estimate
  and ignores the call-site fallback constant. A 60-second learned media-index
  step therefore advances over 60 seconds rather than reaching 95% after the
  old hard-coded 15 seconds.
- Reassurance thresholds use `step_elapsed_sec` in plan mode, so time spent on
  earlier media indexing does not trigger GPU warmup warnings prematurely.
- Legacy/non-plan status payloads retain the old `eta - elapsed` display rule;
  plan payloads display the already-computed whole-startup remaining ETA.
- Added DA3 and RM TRT steps to the overlay fallback ordering.
- `step_progress` is consumed even without an active plan and is no longer
  leaked into the public status payload.

## Startup plan profile-switch correction

- Fixed `reconfigure_startup_plan()` treating an estimate-profile change as a
  removed step. Removal detection now compares stable step keys, not provider-
  specific history keys. Switching `ort_iobinding_runs` from `@pending` to
  `@trt`/`@cuda` therefore does not write a false 0.01-second pending sample.
- The synthetic `pending` profile is never learned. Existing polluted
  `ort_iobinding_runs@pending` values are ignored and removed on load, so the
  pre-validation plan always retains its conservative default budget.
- Deterministically skipped steps now assign 0.01 seconds directly instead of
  passing through the normal timing EWMA. A step that previously took 45 or 60
  seconds converges on the very next successful skipped startup rather than
  requiring roughly ten starts.
- Added regression coverage for profile switching, polluted pending-history
  migration, pending-key absence after persistence, and one-start convergence
  from existing long-duration history.

## Long TensorRT build guidance

- Added structured `trt_building`, `trt_build_model`, and
  `step_estimate_sec` startup fields for operations that are actually building
  an engine rather than loading an existing cache.
- Covered build paths:
  - repaired realtime RVM TensorRT cache (minimum initial budget 300 seconds);
  - uncached DA3 2D-to-3D engine (minimum 120 seconds);
  - uncached mosaic-restoration engines (minimum 180 seconds).
- A build-time minimum overrides a previously skipped 0.01-second history
  value in memory. This keeps the global progress and heartbeat aligned with
  the newly active long build while retaining slower machine-specific history.
- The startup overlay immediately shows a localized explanation that TensorRT
  is generating a GPU-specific engine, an approximate number of minutes, a
  request to keep the application open, and the fact that later starts will be
  faster because the result is cached.
- Cached engine loading does not show the first-build guidance. Transient build
  fields are cleared automatically when the startup step changes.
- Added zh_CN/en_US/ja_JP model labels for realtime matting, DA3, and mosaic
  restoration plus regression tests for minimum-budget restoration and the
  visible two-minute DA3 guidance.

### Review follow-up: cached-load paths also need a floor

The first version passed `minimum_step_estimate_sec=None` when the engine cache
was already present, so only builds were protected. Loading a cached DA3 or
mosaic-restoration engine still takes tens of seconds, and if that step's
history had previously been learned as skipped (`0.01s`), the bar and ETA
dropped to the end of the segment immediately and then sat still for the whole
load. Measured before the fix:

```
t= 1.5s prog=0.0186 eta=5.0 step_est=0.1
t= 5.6s prog=0.0186 eta=5.0 step_est=0.1
```

The DA3 and mosaic-restoration call sites now pass `30.0` for the cached-load
case, matching the `start_heartbeat` constant already used on the same line.
After the fix:

```
t= 1.5s prog=0.0436 eta=33.5 step_est=30.0
t= 5.6s prog=0.1601 eta=29.4 step_est=30.0
```

`tests/test_da3_download_and_trt.py::test_startup_warmup_budgets_the_step_even_when_the_cache_is_present`
covers both `cache_present` values and fails if the floor is removed again.
