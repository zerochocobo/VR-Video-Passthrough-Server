# HANDOVER 2026-07-25

## Investigation: server exits before warmup after NVIDIA driver update

User report: startup UI showed `server process exited before warmup completed`.
No detailed log was supplied. The user had updated the NVIDIA driver; deleting
and reinstalling the application made startup work again.

### Findings

1. The displayed sentence is not the underlying error. It is synthesized by
   `ui/main_window.py` when the child process stops before the UI observed the
   `listening` phase and the last status has no detail. It can represent a
   normal Python exit code 1, a missing-status race, or a native CUDA/TRT crash.
2. NVIDIA driver version is included in both the TRT fingerprint
   (`utils/trt_manifest.py`) and the general GPU warmup key
   (`utils/gpu_runtime_cache.py`). A driver update therefore invalidates both.
3. The normal server-start path does **not** rebuild stale TRT engines:
   - `ui/settings.py::server_env()` only enables TRT when `cache_status()` is
     already `ready`.
   - `main.py::_validate_tensorrt_provider()` rechecks the manifest; if stale,
     it removes `TensorrtExecutionProvider` and falls back to CUDA EP.
   Hence a stale TRT cache alone should not prevent startup and is unlikely to
   be the direct cause.
4. A changed GPU warmup key does cause the mandatory resident CUDA warmup to
   run again. Any Python exception in that warmup is deliberately fatal in
   `main.py` (`return 1`). A driver/runtime incompatibility, CUDA EP failure,
   NVRTC failure, allocation failure, etc. can therefore stop the server.
5. When the warmup key changes, the implementation reruns warmup but retains
   the old directories:
   - `runtime_cache/cuda_compute_cache`
   - `runtime_cache/cupy`
   - `runtime_cache/ort`
   - `runtime_cache/trt_engines`
   There is no driver-version namespace and no targeted cleanup before the new
   warmup. Reinstalling under the same application root can remove these
   artifacts, which explains why reinstall can repair the issue even though
   the program binaries did not materially change.
6. The strongest candidate is therefore stale/corrupt GPU runtime cache or a
   transient driver/CUDA initialization failure during resident warmup, not TRT
   regeneration itself. If the child died by native access violation, Python's
   warmup exception handler would never run, exactly matching a generic UI-only
   failure with no traceback.
7. Observability gap: `HiddenProcess.finished(int)` has the real exit code, but
   `ServerProcess._finished()` ignores it and emits only `state_changed(False)`.
   `ui_startup.log` consequently records no exit code. Windows codes such as
   `-1073741819` (`0xC0000005`, access violation) would have been decisive.

### Recommended follow-up

1. Preserve and report child exit code in `ServerProcess` and the startup
   diagnostic report; decode common Windows NTSTATUS values.
2. On warmup-key changes involving `driver_version`, `compute_capability`, CUDA
   runtime, ORT CUDA DLL hash, or CuPy runtime, quarantine/clear only generated
   GPU caches before importing/initializing the heavy runtime. Preserve models,
   user settings, library DB, and unrelated caches.
3. Store generated caches under a fingerprinted subdirectory, especially CUDA
   compute and CuPy caches, so driver transitions cannot reuse old artifacts.
4. Add last durable startup checkpoint to diagnostics (key build, ORT session
   creation, TRT static preload, first inference, composite JIT), because native
   crashes cannot be caught by Python.
5. Optionally retry once in CUDA-only safe mode after a pre-listening GPU crash,
   with freshly isolated caches; do not loop indefinitely.
6. Ask affected users for `debug_output/server.log`, `ui_startup.log`, old/new
   driver versions, and Windows Event Viewer faulting-module/exception-code data.

No production code was changed during this investigation.
